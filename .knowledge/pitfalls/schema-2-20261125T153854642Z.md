# 现象

容器 `bug-fix-batch-1116` 修 bug `aac1a701`（resolve_bug 返回值与 output schema 漂移：schema 要 `{card}`，execute 返回裸 card）。任务 brief 把「用 resolve_bug 回填本 bug」写成真机验证条件，worker 自报「首次回执报旧 schema 错、服务端已落终态；构建后二次调用回执通过」。独立评审证伪该证据，两点：

1. **写入先于校验**：`createResolveBugTool` 的 execute 是先 `await bugsOf(deps).resolveBug(...)` 落库，再包装返回；output schema 校验在 harness 侧对返回值进行，发生在 execute 之后。所以只要服务端写入成功，回填就成功，`get_bug` 复读 status=fixed 也只证明写入。
2. **宿主仍装载旧构建**：live 世代里 project 包是 0.35.1（修复是 0.35.3），`dist\host\index.js` 的 mtime 早于两次提交，里面仍是 `const v = value; v.bugStatus` 的裸 card 读法。worker 看到的「第二次通过」不是修复生效的证据。

# 判据

- 「工具自身回执」类真机证据的成立条件：被验证的是**回执形状**时，回执必须来自装载了修复后构建的宿主；被验证的是**服务端状态变更**时，复读（get_bug）才是证据。
- 核销装载面（无需重启）：读 `%DSH_HOME%\profiles\.generations\live\<世代>\node_modules\@dsh-forge\<pkg>\package.json` 的 version + grep 该包 dist 内目标函数的写法；版本或写法不符即停，不采任何取证。与 `official-host-install-generation-channel`（打包→正式安装→manifest 双校验）同口径，本条是它在「修复循环内 worker 自证」场景的应用。
- 修复类任务的 brief 与 AC：**不得把「回填本 bug」写成真机验证**；回填只作台账闭环，真机证据单列并标明取证环境，或以 `evidence_debt` 声明欠账。
