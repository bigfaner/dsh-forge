# 删依赖后的锁文件差异：逐项反查归因配方

## 适用

删除包或依赖声明后，spec/评审要求「锁文件其余差异仅为只被被删方声明的依赖及其子树，逐项给出反查依据」。

## 配方

1. **定基线**：`git diff <改动前 commit> -- pnpm-lock.yaml apps/host/profile.dev/pnpm-lock.yaml`，两份锁都比
2. **列消失条目**：importers 段的整块、packages 段的包键、snapshots 段的 peer 变体——三类分开列
3. **逐条反查声明方**：在**基线**上 `git grep '<包名>' <基线> -- '**/package.json'`，列出所有声明方，确认全在已删范围内
4. **peer 变体要追 peer 链**：消失的往往不是包本身，而是某个 peer 组合的变体——该变体的 peer 链里有某版本的包，而那个版本的唯一直接声明方是被删的包
5. **反向核对**：仍在锁里的每个包至少有一个现存声明方（抽查即可）
6. **真机实证**：`pnpm install --frozen-lockfile` 锁文件 git 干净——但这只证锁文件自洽，**不证依赖目录物理完整**（见 `pnpm-virtual-store-junction-empty-dir`）
7. **结论写进提交说明**：消失清单 + 每项反查依据 + spec 预估与实测的差异说明

## spec 预估 ≠ 实测

spec 在写方案时预估「哪些第三方包会随被删包出清」，这是**预估**。实测常不符——判例里 spec 预告三个包出清，实际一个都没出（各有其他消费方），倒是另一个没预告的 peer 变体出清了。

**如实记录差异，不迁就预估**。预估错了不是问题，把预估当验收标准才是。

## 归因产物不要只留盘上

判例里归因结论写在空提交的提交说明里、明细在 `.forge-tmp`——`.forge-tmp` 不入 git，clone 后只剩提交说明。要么把明细表也写进提交说明，要么归到入库的位置。

## 判例

容器 `plugins-remediation-m1-legacy-retirement` 任务 2.4 / 4.4（2026-11-28）：根锁 -76/+0，消失项 = 两个旧包 importer 块 + 一个 `dsh-subagent-in-process-driver@0.2.0-rc.2` 的 peer 变体；profile.dev 锁 -6/+0。spec 预告的 `ajv@8.20.0` / `dsh-llm@0.2.0-rc.2` / `dsh-session-projection@0.2.0-rc.2` 实测均仍在。提交 `e31bbf00`。
