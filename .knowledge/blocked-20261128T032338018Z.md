# 任务循环的机械门以「单卡自足全绿」为前提，而拆解按跨卡分工组织

## 现象

一个任务循环里连续多张卡以 blocked 结算，每张的根因表面不同，但都是「worker 把本卡范围内的事做完了，门却因为卡范围之外的东西不放行」：

- 删了包，门要求全仓测试绿，而处置那些测试是另一张卡的活
- 改了文档，门要求跑门禁和 git commit，而该类型 worker 没有 shell
- 实现已提交、定向测试全绿，门要求 `gate_test=true`，而全量有基线既有的红
- 实现完成，门因「无提交」判无进展，而该卡本就不产出提交

主会话每次都得人工兜底：读 worker 的取证、独立复核、代结算或代提交。

## 机制

task-loop 的结算门有四类，各有各的判据，但共享同一个隐含前提——**一张卡应该能靠自己让门全绿**：

| 门 | 判据 | 与跨卡拆解的冲突点 |
|---|---|---|
| `gate_test` 强制 | 带 AC 的 success 须 `gate.test=true` | 卡只负责实现、测试同步在下游卡时，本卡无法真报 true |
| 证据门 | evidence 里的路径须在盘 | 无 shell 的卡落不了盘 |
| 阶段门 | 验证类卡须等实现链全终态 | 验证类卡若在实现链上游即成环 |
| 派生债卡 | 按 facets 自动派生 test-run | spec 已声明不真跑时，派生的卡与 spec 冲突 |
| 无进展启发式 | 按 commit 计数 | 核验卡、文档卡本就不产出 commit |

拆解（to-tasks）的粒度原则是「一任务 = agent 一次可独立收口的委派粒度」，天然产生跨卡承接：A 卡删东西，B 卡修被 A 弄红的测试。这与门的「单卡自足」前提直接错配。

## 判例

容器 `plugins-remediation-m1-legacy-retirement`（2026-11-28）：18 卡，4 次 blocked，3 次同源（2.2 / 1.4 / 2.6），主会话兜底 4 次。飞轮指标一次通过率 1、返工比 0，但端到端无干预通过率 10/14——**指标看不到主会话的兜底**。

## 规避

**拆解期**（最便宜）：

1. 删东西与修被它弄红的测试放同一张卡，或让删东西的卡 AC 写明「本卡不要求全仓绿，定向池绿即可」
2. 类型选择对照「该卡产不产出交付物」：产出文件（含锁文件、配置）的是实现类，不是 `validation-*`
3. 需要提交或跑门禁的卡，不派无 shell 的类型（`doc-drift` 等）；若必须，简报写明「门禁与提交由调度方代执行」
4. spec 声明不真跑 e2e 时，预期循环仍会派生债卡——拆解期就在 brief 里写「债卡预期 skip」，省得结算时才处理
5. 拆解前产出一份 HEAD 存量红清单（类型错误、已知红的测试），写进每张卡的结算口径

**结算期**：worker 撞门时，正道是「先提交 + 落盘 resume.md + blocked 上浮」（见 `blocked-resume-md-handoff-format`），不越界修、不虚报门。

**机制层**（未修，三条修复方向）：门参数化（基线红清单 + 范围 = 定向池）；进展信号纳入落盘证据而非只数 commit；阶段门读依赖边而非只看类型。
