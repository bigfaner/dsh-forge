# 派发前对照能力面：worker 类型决定工具面，评审类派发须带专家档案

两条同一主题——**派发前先查「谁来干、它有什么工具」**。

## 一、无 shell 的 worker 类型不得配需提交的 AC

### 现象
`doc-drift` 类型 worker 的 toolFilter 不含 shell。文档全改对、AC 全验，仍无法跑门禁、无法 `git commit`，只能 blocked 上浮。主会话代执行门禁与提交后结算。

判例：plugins-remediation-m1-legacy-retirement 任务 2.6（2026-11-28），worker 在 audit-evidence.md 里自救式写明「本子会话无 shell——门禁与 git commit 由调度方执行」并列出命令清单。

### 机制
task-loop 按任务类型配 toolFilter。`coding-*` 类有 shell；`doc-drift` 等文档类没有。拆解时选类型只看了「这是文档活」，没看「这个类型能不能提交」。

### 规避
- 需要提交或跑门禁的卡，不派无 shell 类型；文档改动若需提交，用 `coding-cleanup` 或 `doc` 等有 shell 的类型
- 若必须用无 shell 类型，简报写明「门禁命令与 add 清单交调度方代执行」，AC 写成「改动落盘 + 取证」而非「已提交」
- 这是 worker 环境限制的第四条（前三条见 `worker-session-environment-limits`：专家池只见用户层 / addTask 被拒 / sessions 直读受限）

## 二、评审、裁决、收口定性类派发须走专家

### 现象
循环收口的「派多个 subagent 分域交叉评审」，主会话按字面用 `subagent` 工具派了三个裸子代理、各配手写 prompt。专家注册表里 `architecture-reviewer` / `code-reviewer` / `retro-reviewer` 三个对口岗位闲置。用户指出后中断重派。

更深一层：手写 prompt 里塞了主会话的预判（如预先声明「某处内联实现不在收敛范围、区分对待」）——评审员顺着这个框走，**名为独立评审，实为确认主会话想法**。

### 判例对照
改派专家后：架构评审抓出文档悬空引用（裸评审 prompt 没问文档），代码评审抓出 AC7 的 18 处测试字面量（架构评审漏了）——**两路各漏一样，交叉才补全**。三个共享主会话盲区的裸 subagent 做不到这个。

### 规避
- 评审/复盘/裁决类派发前先 `list_experts`，有对口岗位一律 `delegate_expert`
- prompt 只给评审对象与事实范围，**不给主会话对结论的预判**
- 专家不可用（not found）时的代行法见 `expert-registry-stale-snapshot-delegate-not-found-persona-proxy-subagent-standin-new-archive-visibility`（携档案路径读档）；本条讲的是「有专家时必须用」
- bug：`a81d1d99`（expert-system-bypassed）
