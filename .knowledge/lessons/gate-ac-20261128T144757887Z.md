# 收口门「全量矩阵通过」与存量红：派发前先定口径

## 问题

规格里写「零行为变更」的迁移类批次，收口 gate 任务的 AC 写成「`npx vitest run <全量矩阵>` 通过」。但主分支本身带着一批存量红（本例 62 例：上游 pin 版本漂移、BOM、死锚、环境缺口），gate 任务从第一次跑起就不可能达标——只能 blocked 上浮，再由人判断哪些是存量、要不要清、清到什么程度。同一容器里 gate 任务因此阻塞两轮，共约 35 分钟耗在重跑既有红面上。

## 教训

- **写 gate 任务 AC 时区分「本批回归」与「存量红」**：规格编制阶段就跑一遍全量矩阵，把批前失败清单冻结进规格或任务简报；AC 写成「失败集 = 已登记的存量红集合，集合外零失败」。
- **存量红的处置范围是产品/流程决策**：清不清、清哪些，由用户裁决（本例用户先选「清账后再收口」，后又裁定部分项「不碰」并授权条件跳过）——不要由 worker 或主会话自行扩张或放宽。
- **归因要有基点证据**：说「存量红」须附批前基点的字节或提交对照（如 `git show <base>:<file>` 的首字节、目录删除提交号），不能凭 worker 口头结论（本例 worker 报的 BOM 编码形态有误，结论碰巧不变）。
- 已有相关条目：欠账任务绑在存量红上一跑即红（见 `fix-2` 判例）、全量门基线消歧（指纹清单兜底）——本条补充的是「gate 任务 AC 的写法」这一前置点。
