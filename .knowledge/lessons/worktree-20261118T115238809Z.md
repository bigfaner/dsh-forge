# 判例：共享 worktree 并发会话工作树互踩（bug 2d4e173a / a6b4eb6e）

## 现象

同一天内两起工作树污染，均发生在多会话共享同一 worktree（Z:\...\worktrees\plugins）期间：
- 1.18 提交清 BOM 后，两测试支撑文件被并发 e2e 会话在途编辑重新写入 BOM + 内容回退（未提交态）；
- hif 修复链的在途 spec.ts 改动（+13/−2）滞留工作树，与本提案循环收口的「git status 干净」门互斥，三路评审反复点名。

## 根因

worktree 是多链共享的物理面，而 git status 是**全局单值**——任一会话的在途编辑都会污染所有其它链的收口判定；且并发写入方无感知（各会话只看自己的任务面）。

## 规避

1. **收口门前先排查归属**：发现非本链工作树改动，先判定写入源（在跑会话/已完成遗留）——盲覆写会毁掉并发会话在途工作（BOM 复染处置即按此纪律先定谳再恢复）。
2. **在途改动按归属链单独成提交收敛**（先例 e030e2dd / feea00cb：提交说明显式声明归属他链 + 共 worktree 在途定谳），不混入本链提交、也不无限期滞留。
3. 写文件一律 node/工具往返（禁文本替换重写）——并发会话可能用劣质写径（本案 BOM 即来自并发侧写径），提交态是唯一可信基线。
4. 结构性防复发（收口卫生门、会话-worktree 绑定）归改进提案，不在本判例展开。
