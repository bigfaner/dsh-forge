# Proposal: dsh-forge 重构总纲 —— 以知识资产为核心的研发工作台（AI Coding 场景切入，零代码分支重开）

> **接管说明（2026-10-02）**：本提案沉淀 M1–M4 迁移经验后，**从零重新设计**产品形态与数据模型，替代既有路线（`proposals/dsh-forge` 及其 M2–M4 演进链）成为方向权威。既有提案不删除，保留为教训与参考。实施载体为**零代码新分支**（详见 Scope）。

> **文档性质（2026-10-02 定格）：本提案 = 项目总纲，不直接进入实施。** 其中三部分内容具有**宪法级约束**力：定位与边界（§产品定位 / §数据模型 / §写入边界）、工件版图（§产品形态 / §forge 插件 / 知识插件）、演进路书（§演进路书 P0–P5）。一切阶段提案不得与之冲突；修改总纲须显式提案推翻。**实施节奏 = 分阶段、一阶段一提案**：每阶段按 §演进路书 立项独立提案（slug 约定 `dsh-forge-p<N>-<主题>`，走 PRD→设计→任务管线），阶段提案继承本总纲的 SC 相关断言，并在其范围内细化验收。模块与包的能力边界落实见配套**《架构基线》**（`architecture.md`，宪法级原则的技术配套，随阶段设计细化）。

## Problem

核心问题一句话：**dsh-forge M1–M4 迁移的产出未达到用户预期。**具体表现在三个层面。其一，工作台 UI 与上游 dsh 的会话体验割裂，打磨粗糙。其二，「文件 SoT + SQLite 投影」的双层架构引入了投影、快照、回流等派生概念，认知与维护成本高于收益。其三，产品的职责边界——应用管什么、不管什么——从未被清晰划定。

**产品定位（2026-10-02 定向）**：核心卖点 = **知识抽取与管理，深度契合 AI Coding 时代的研发流程**。产品把经验显性化为知识资产、把研发流程固化；用户通过管理知识资产、设置项目约束、标准化流程来管理项目。**知识资产是最重要的资产**。当前切入 AI Coding 场景，未来可能切入其它场景。架构上的薄状态层（见下）是手段，知识资产复利才是目的：抽取 → 置信度筛选 → 复用 → 再沉淀的飞轮。

### Evidence（经验沉淀，四条核心教训）

1. **「必备插件 + 上游 home 增强层」路线天然产出嫁接感**。M4 选择在上游 dsh home 上做槽位注入增强（`packages/plugins/forge-workbench`），视觉与组件受上游令牌和 0.1.6-alpha peerDeps 锁死，打磨上限被结构性封死——落地体验与验收原型（`docs/features/dsh-forge-m4/ui/prototype/`）差距显著。产品级 UI 需要自己的主场。
2. **投影/双 SoT 的复杂度反噬**。M4 的 workspaceRegistry 单向投影（forge 文件 → SQLite 快照）加上 DF003 感知回流，是「文件为 SoT + 结构化需求」的折衷产物。用户明确否定此类派生概念：**SoT 边界应按资产类型一次划清，而非运行时双向折衷**。
3. **里程碑语言与用户心智系统性错位**。用户预期「M4 达成后去掉工作台插件」，而既有决议⑧明确「forge 核心 = 必备插件、不可禁用」——M4 退役的是 Claude Code 插件。决策日志记录的是技术语义，未核对用户心智模型，导致"完成"≠"达成预期"。
4. **薄产品职责从未定义**。M2–M4 持续加码（投影、归档、多窗口、文档管理、知识库挂载……），应用逐渐变成"什么都管"的重产品；用户实际要的是**状态层 + 只读引用**的薄产品。

### Urgency

- 现有增强层路线每多迭代一步，嫁接感债务越深，重写成本越高。
- M4 已完成、遗留项（20 技能/四动词/影子 git）顺延未清，正是路线重审的天然窗口。
- 用户对当前产品的信任已受损，继续在旧架构上打磨只会加深"失望-修补"循环。

## Proposed Solution

**从零设计薄状态层产品**：应用只做「结构化状态 + 只读引用 + 会话编排入口 + 知识资产全链路」，不管文档内容创作（归技能）、不管代码仓。**归零设计但锁定 dsh 为 agent 运行时**（从需求推导，不预设架构）。

**产品形态（2026-10-02 修订，替代原「场景分层」定向）**：产品恒为 **forge 产品**——有且只有一个场景（AI Coding / forge 管线）。数据模型、API、UI 直接表达 forge 场景语义（状态机词汇、管线动词、看板视图），**不设场景中立的中间层**。原「场景无关内核 + 场景包」两层模型退役。

在此原则下，各部分的定位如下：

- **产品能力模块**：知识资产全链路（存储/抽取/置信度/召回）、会话/工作区挂接、任务/feature/提案状态层、三区工作台。模块与包的能力边界见配套《架构基线》（`architecture.md`）。
- **独立工件**：forge 插件（管线技能 + 命令 tool）与知识插件。切分动机是代码管理与迭代节奏（含 dsh tool 须以插件形态注册的机械要求），**不承载运行时可替换承诺**。
- **通用基础能力在迭代中沉淀**：仅当能力在真实使用中证明通用，方提炼为独立基础包（证据驱动，非预设）。未来切入新场景 = **基于沉淀的基础能力快速搭建新产品**（届时另立提案重新决策），而非同一产品换装场景包。

### 数据模型（单一归属，无投影）

每类资产**有且仅有一个归属**，不存在派生快照：

| 资产 | 归属（唯一 SoT） |
|---|---|
| 任务清单 / 执行记录（forge 运行时资产） | **应用运行时存储**（不进代码仓） |
| 任务/feature/提案状态、任务↔会话挂接元数据、视图状态 | **应用数据库**（注：任务↔会话挂接 = 应用侧关联记录；dsh 会话账本本体归 dsh，见 §项目↔工作区映射） |
| proposal / PRD / tech-design / ui-design | **默认代码仓内；项目注册时可选仓外** |
| 项目级知识 | **仓外独立目录**（随项目） |
| 全局知识（经验/专家/通用规则） | **独立全局库**，多项目共享 |
| 测试资产 | **代码仓内** |

> **存储术语约定**：全文「应用数据库」指唯一 SoT 存储本体（引擎设计期定）；「应用运行时存储」指其在应用 profile 下的部署位置；「应用状态层」指其数据访问面；「宿主能力面」指宿主对外暴露的服务 API——UI 管理面与插件 tool 面都是它的消费端。

应用写入边界（总纲）：**代码仓与文档位置（PRD/设计/测试资产）只读**——应用仅做渲染展示与路径跳转，不做管理/迁移/导出，也不做上下文注入（知识的使用由 agent 自行决定）。**知识目录是唯一例外**：经宿主能力面（UI 管理面 / 知识插件写入 tool）写入，详见 §知识抽取与置信度·写入边界。

### 产品形态（UI/UX 基线 = 重构原型，2026-10-02 切换）

三区单工作台页，以 `docs/proposals/dsh-forge-redesign/prototype/`（2026-10-01，可交互 HTML 原型 + 冒烟断言）为交互骨架基准；M4 验收原型降级为 dsh 原生 UI 对齐参考（未显式移除元素对齐 dsh/M4 基线）：

- **左栏 = 菜单与导航**：品牌行（整块 = 新会话快捷）/ 新会话 / 知识库入口（带待审核徽标）/ 项目树 + 会话列表（dsh 行语言）/ 设置；可收起为 56px rail；
- **中区 = 一等公民视图互换**：会话面板（对话 / 轨迹 / 知识召回 tab）⇄ 知识库面板（浏览 / 统计分析 / 召回日志）**整体切换**——知识模式无右栏入口（已展开也隐藏，状态保留，切回即恢复）；
- **右栏 = dock 页签容器**（默认收起，轨道归零）：概览 / 文档 / 审核台 / 知识文档页签；**dock 页签跟随所属项目**（可见集 = 当前项目 + 全局页签，切项目页签集切换不打断面板，切回即恢复）。

与 M4 的本质区别不变：该三区页是**新产品的原生首屏**（自有主场与设计体系），不再是上游 home 上的增强层。

### UI 资产复用策略（源码复核 2026-10-02，上游 `Z:\project\github\deepseek-harness`）

上游官方机制（apps/web vite.config 明注）："Plugin packages never enter this graph; they arrive as runtime bundles through the client module system"。即构建期只产出**壳**（`@deepseek-ai/dsh-client-web`：boot 内核 = 静态模块表 + Cordis loader）；ui-* 插件包**不进构建图**，运行期由宿主经 `window.__DSH_BOOT__` boot manifest（injections）+ `applyIndexInjections` 动态加载，`__DSH_TRANSPORT__` carrier 接 RPC。

**本产品采纳的模式**：

1. 自有 vite 前端入口（仿 `apps/web` 模式），复用 `dsh-client-web` 壳内核——产品 shell 是自己的入口，不存在"住进上游 home"。
2. **boot manifest 由产品掌舵**：选哪些 ui-*（ui-sidebar / ui-chat / ui-conversation / ui-dockkit / ui-theme…）的 client bundle 进入产品。它们经产品自己的 manifest 成为**产品 bundle 的组成部分**（非第三方运行时插件）。
3. 库性质包（ui-theme 令牌、ui-primitives）可静态库消费，作为自有设计体系基座。
4. forge 专属 UI（知识面板、项目树增强、dock 面板）做成产品自有 client 插件，与上同机制共存。
5. 否决"把 ui-* 静态打进 dist"——那是与 client module system 对抗的重度 fork，升级合并成本高，非最优。

**Markdown 渲染复用（2026-10-02 定向）**：正文渲染一律复用官方 `ui-primitives` 的 `MarkdownText` 族（不可信 GFM + TeX、流式增量渲染、`MarkdownDelegateProvider` 文件链接行号跳转 `#L24`、`pathImages` 本地图片）——知识详情抽屉 / dock 知识文档页签 / 文档 tab（proposal/PRD/design 只读）/ 抽取稿预览统一消费，**不自制渲染器**；会话面板经 ui-chat 同源，视觉一致由同组件 + `--dsw-*` 令牌双保险。**风格一致为硬纪律**：产品内唯一包装入口（`MarkdownDoc`）+ variant 判定规则（文档面 `body` / 嵌入预览 `compact`）+ ui-primitives 与 ui-chat 版本锁步 + 跨面 computed style 机械断言——细则见《架构基线》。

**槽位可替换性（sidebar 示例，源码核实）**：官方 ui-sidebar 本质只是 `'sidebar'` 槽位的占用者（`ctx.slots.inject('sidebar', ...)` 注册槽位树：`sidebar.workspaces` / `sidebar.panellist` / `sidebar.settings` 等子洞）；ui-workspace 等生态插件不依赖官方包本身，只按洞名注入（`inject('sidebar.workspaces', ..., WorkspaceBrowser)`）。替换有两条路线：**A（默认）保留官方 sidebar 壳，自有插件替换 `sidebar.workspaces` 占用者**——自有项目树/知识面板，成本最小，壳的折叠/导航/快捷键白拿；**B 整壳替换 `'sidebar'` 槽位占用者**——须复刻槽位契约（洞名 + injected props），契约漂移风险自担。无论 A/B，均为清单级增删，不碰前端构建。

**风格一致纪律（ui-theme 令牌系统，源码核实）**：视觉一致性由 `ui-theme` 运行时注入的三层 CSS 变量保证：`--dsw-static-*` 调色板、`--dsw-alias-*` 语义别名（含深浅双主题）、`--dsw-specific-*` 区域特定，另有 `--dsw-radius-*`、`--dsw-font-*`（随用户字号偏好联动）、`--dsw-elevation-*` 与 focus 规范。自有组件硬纪律：**样式只引用 `--dsw-*` 变量，禁止裸色值/裸字号**——由此自动获得同视觉语言、主题切换、字号联动；基础组件优先复用 `ui-primitives`（本就吃令牌）。

命名辨析（避免误引）：`@deepseek-ai/dsh-web`（packages/web/web）是 ctx.web 能力插件，与 UI 无关；`packages/host/*` 是宿主侧插件；`apps/web` 与 `apps/desktop-host` 是应用。

### dsh 源码 vendor 裁决（发布状态核实 2026-10-02）

上游 npm 发布状态：`@deepseek-ai/dsh`（CLI/profile-boot）、`dsh-client-web`（壳内核）、全部 `ui-*`、`dsh-host-webserver`、`dsh-workspace`、`dsh-app-boot` 均 **public**；唯一 **private 不发布**的是 `@deepseek-ai/dsh-desktop-host`（Electron 宿主进程，本体仅 ~122 行 main + office/更新/退出巡检附件，其全部依赖均为公开包）。裁决：

- **主线 = B 自写薄宿主**：自有 ~100 行宿主入口（`loadProfileDirectory` + `runProfile` + `{url, injections}` IPC 上报），依赖全走 npm 公开包，**彻底去 vendor**——与零代码新分支的纯净起点一致。
- **fallback = A 继续 vendor desktop-host**（现行 `packages/desktop-host-vendor` 模式）：仅在 B 的 spike 失败（runProfile 等 0.x API 不可用/面不足）时启用。
- 前端/UI 侧零 vendor（全 npm 依赖 + 版本精确锁定）。

### 知识库数据形态与视图（2026-10-02 定向）

**知识一律以 Markdown 文档承载**；frontmatter 承载结构化元数据——摘要、**关键词（域内细分）**、状态、作者、修改时间等。应用解析 frontmatter 驱动两级视图：

- **知识列表页**：各知识卡片由 frontmatter 字段构建（标题/摘要/关键词/状态/时间等，支持按关键词、状态过滤）；
- **知识详情页**：基础信息表单区展示 frontmatter（只读渲染），文档区只展示正文（frontmatter 不混入正文显示）；
- **热度展示**：知识卡片与详情基本信息区均展示**热度 = 被引用（召回使用）次数**——数据源为召回使用事件（应用状态层），与置信度的使用信号同源。

**目录即域（2026-10-02 定向，OpenViking/DSQ 研究吸收）**：知识目录树即分组与域作用域。**一级目录 = 最大域**，目录**最多三层**（如 `编程/java/安全`）。**域由目录路径派生，frontmatter 不重复声明**（单一事实源零漂移）；**关键词负责域内细分**（`安全/` 下通用规则 vs 特定框架靠关键词区分）。跨域知识放共享域目录（与各域平级）。召回的域过滤 = 目录路径前缀匹配（DSQ 浅树版）；换域 = 移动文件（结构维护见 §知识库工程机制）。

约束：frontmatter schema 为应用与技能双方共享的契约（技能/agent 写知识时须带合规 frontmatter 并遵守目录层级约定）；正文与元数据分离渲染；详情基础信息表单为只读展示，元数据编辑经宿主能力面的 UI 管理面或知识插件写入 tool 完成（见写入边界）。

### 知识库工程机制（OpenViking/arXiv:2606.16903 研究吸收，2026-10-02）

- **结构维护（DSM 轻量版）**：知识条目持**稳定 ID**——载体 = frontmatter `id` 字段（新建时生成、随文件移动而不变）；索引只存 **parent 引用**、不存全路径投影（论文证明祖先物化导致 MOVE 写放大）；目录/文件的移动、改名、合并 = 宿主能力面封装的单一 API（文件操作与索引同步一体，参照 VikingFS mv/rm）；合并带同名冲突策略。
- **外部修改对账（目录可被编辑器直改直移）**：知识索引 = **可随时重建的派生缓存**（非 SoT——SoT = 知识文件 + 应用状态层），故不违反无投影纪律。**启动时及进入知识面板时对账**：扫描目录按 frontmatter `id` 重新挂载索引，索引缺失条目重建、文件缺失条目标记失效待清理。此为**按需一次性重建**，非运行时 watch/回流（SC2 所禁的是后者）。
- **全局库位置**：独立全局知识库 = 应用 profile 下的专用目录（多项目共享；具体路径设计期定）。
- **排序与置信解耦**：相关度排序**不直接由使用频次驱动**（OpenViking 实证教训：频次参与排序会形成热度反馈回路）——置信度用作**召回阈值与 UI 徽章**，引用次数设上限/衰减防自我强化。
- **条目粒度**：单条知识目标 ~300–800 token；**摘要先行**（卡片/召回注入以摘要为主），正文按需读取。
- **上下文打包预算**：召回注入带 token 预算 + 置信阈值（参数设计期定；OpenViking DSH 集成的 2000 tok / 0.35 为外部参考值，非硬依据）。
- **召回可重放**：召回事件落会话记录（durable message 思想），抗上下文压缩，亦为使用监控面板留数据源。
- **抽取去重**：抽取时做关键词/n-gram 近似检测，疑似重复进入**合并审核队列**（人工或 agent 合并）。
- **两层晋升流**：项目级知识 → 全局知识的**晋升审核动作**。晋升 = **移动**到全局库，项目侧留重定向记录（指向全局条目）；全局已有同名/近似条目时进入**合并审核队列**（与抽取去重共用队列与 UI）。
- **漂移检测与纠偏（未来实现，2026-10-02 记账）**：知识随项目演进而失真（约束过时、经验失效、条目间冲突）。检测信号：知识内容与代码/文档现状的偏离、同域知识间的语义冲突、使用信号骤降；纠偏动作：标记待复核、触发重审或更新建议（agent 比对现状生成修订稿）、归档淘汰。v1 仅保留置信度衰减作最简兜底，完整机制未来独立设计。
- **延后锚点（触发条件再启）**：层级语义深扩展（单域 >1k 条再引入目录键展开）；向量/语义检索（关键词召回不足时；最轻路径 = 宿主进程内 ONNX 嵌入 + flat 余弦，维持零外部服务纪律；不引入 OpenViking 本体——AGPLv3 传染 + 独立 server 违背单机轻依赖）。

### 知识抽取与置信度（2026-10-02 定向）

**抽取**：从会话对话中抽取知识沉淀入知识库。触发两路——用户主动（知识面板动作）或 agent 自动；抽取执行归 agent 会话（应用只提供入口与存储面）。

**置信度（动态计算，非静态字段，四信号）**：

- 新抽取知识**未经审核，初始置信度中等**；
- **提升信号**：人工审核通过；被 agent 多次使用（次数 + 近期性加权）；agent 显式反馈采纳；
- **降低信号**：未经人工审核且长期未被使用（时间衰减）；agent 显式反馈忽略；
- 置信度**读取时动态计算**——由审核状态（frontmatter 状态字段）+ 使用记录（应用状态层：次数/最近使用时间）+ 显式反馈记录 + 时间衰减函数四信号合成，不落盘存储，杜绝存储值与信号漂移。

**置信度 → 召回**：agent 召回知识时置信度参与排序与阈值过滤（低置信知识降权或不召回），具体权重/阈值设计期定。

**写入边界（2026-10-02 修订并统一口径）**：知识目录的**一切写入经宿主能力面**——两条入口同一后端：① UI 管理面（用户的增删改/审核/移动/晋升操作）；② **知识插件写入 tool**（agent 会话中"调整知识资产"由此走——带契约校验，与 UI 同一 API，索引同步一体）。**不存在绕过能力面的 agent 直写文件路径**。零写入纪律仅适用于**代码仓与文档位置**（PRD/设计/测试资产）。

### 项目 ↔ 工作区映射（引用而不复制）

dsh 的 Workspace（`@deepseek-ai/dsh-workspace`，经 `ctx.workspaceRegistry`）= 稳定 uuid + canonical path + 有序会话账本。衔接原则：**项目记录持有 `workspaceId` 引用，join key = canonical path；会话列表每次经 dsh workspace API 实时读取，应用数据库不存会话账本副本**。应用侧只存自己的扩展字段（文档位置、知识目录、任务/feature 状态）；dsh 的归 dsh——此为「无投影」纪律在项目映射上的落实。

**具体机制（源码核实，2026-10-02）**：

1. **注册 = 先 dsh 后自家**：`ctx.workspaceRegistry.create(projectDir)` 返回实体（uuid + canonical path）；应用库 `projects` 表只存 `workspace_id` 外键 + 自有扩展字段（文档位置、知识目录、归档态），**无会话列表字段**。`create()` 对同 canonical path 幂等（上游语义 "Returns the existing or newly durable workspace"）。
2. **对账钥匙 = canonical path**：应用库同时存 `ws.path`；启动时校验 `registry.get(workspace_id)?.path === project.canonical_path`，失配则按 canonical path 在 `registry.list()` 中找回，找不回则重新 `create()`（幂等安全）→ 单向修引用，不产生数据复制。**目录整体移动的边界**：旧 workspace 实体仍存于 dsh 侧（其会话历史不丢）；应用侧重新 `create()` 后新引用不含旧账本，允许用户在项目设置中手动挂接历史 workspace 取回会话列表（显式动作，不做自动迁移）。
3. **会话列表实时读**：左栏渲染时直接 `registry.get(workspace_id).sessionIds` → 逐 id 取会话头（标题/状态点/相对时间）；renderer 侧经 `packages/api/workspace-controller` RPC 面等价调用。零缓存零副本，dsh 侧增删天然一致。
4. **写权在 dsh**：会话的 attach/detach/排序由 dsh 侧（会话启动自动挂接或经其 API）维护，应用不写账本。

**与 M4 投影的本质区别**：投影方案存 sessionIds 快照副本，需 watch/感知/回流（DF003）追平；本方案应用只持外键，UI 渲染直问本体——无快照、无回流、无感知机制，概念只剩「外键 + 对账」。

### forge 插件：技能 + tool 合一（2026-10-02 定向）

SDD 管线技能与 forge CLI 转化的 dsh tool **合并为同一个独立 dsh 插件**（forge 插件）——技能（方法论与流程指令）与 tool（命令语义）本就同源同节奏，合一发版、独立迭代：forge 插件的演进与工作台产品（壳/UI/状态层）解耦，可各自发版、互不阻塞，亦可独立分发与启停。应用只看不管（不做原生编排），未来再评估。（后经 §工件版图 细化：forge 插件按模式切分为管线核心/规格深化两包，brainstorm 独立成工件——原则不变，工程形态细化。）

**插件两半身**：

- **skills 半身**：SDD 管线技能（brainstorm→PRD→设计→任务→执行）；
- **tool 半身**：forge CLI 相关命令（任务 CRUD/状态机、feature 状态、**提案状态**、配置等）转成的 dsh tool，消费宿主能力面，向 agent 提供模型可调用的命令语义。

**职责分工**：**宿主暴露能力**——应用宿主（数据内核侧）以 API 暴露能力面（任务状态层读写、项目/工作区查询等；知识召回能力由随产品交付的知识插件消费，不经 forge 插件）；**forge 插件使用能力**——tool 半身消费能力面（任务/管线域），skills 半身编排方法论。

**技能集裁剪（2026-10-02 定向）**：forge 的 eval-\* 系列对抗评估技能**暂不引入**该插件；引用 eval-\* 的技能（如 brainstorm 的对抗评估步、设计/PRD 流程中的评估门）须相应调整——移除或改为可选步骤，不得留下指向缺失技能的悬空引用。

此裁决落实既有方向「CLI 退役终点 = 应用 API + dsh tool，CLI 不保留」：Go CLI 不再随包分发，命令语义由 forge 插件 tool 半身 + 宿主能力面承接。

**召回 = 宿主能力（2026-10-02 定向）**：知识检索/召回是宿主能力面的一部分（知识目录解析 + frontmatter 索引 + 置信度计算 + **域过滤**），由**知识插件**（独立插件，随产品交付，不与 forge 插件关联）暴露为 agent 可调用的 dsh tool。**会话上下文 → 域映射（最简机制）**：项目注册时配置默认召回域（存应用数据库），会话发起时可带域参数覆盖；映射到此为止，不做更复杂的上下文推断。召回过滤 = **目录路径前缀（域作用域，最多三层）+ 关键词细分**（设置极简，不做规则引擎）：前后端混合项目中，前端域召回前端约束、后端域召回后端约束、交互约束放共享域目录；域内先按相关度、再受置信度阈值约束（排序与置信解耦，见 §知识库工程机制）。**约束/规则属于普通知识**（不设 sticky 常驻特权）。**每次召回即记一次使用事件**（存应用状态层 + 落会话记录可重放）→ 次数/近期性 → 置信度信号闭环；未来的知识使用监控面板与此同源。

**召回 tool 面（分层阅读动词集，OpenViking 博客经验 2026-10-02）**：动词集保持极小且可学习——`browse`（域树/列表）、`search`（域+关键词检索）、`read-abstract`（摘要）、`read-full`（正文，按需）；默认返回摘要（token 纪律）。

**召回可解释与反馈（OpenViking 博客经验 2026-10-02）**：召回结果附**命中理由**（域路径 + 命中关键词 + 置信度构成）——agent 据此判断采信，未来监控面板可回答"为什么召回"；召回后 agent 显式反馈（采纳/忽略）记为事件，作为置信度**第四信号**（比隐式使用计数更强的自演化信号）。

**agent 系统提示词的知识段（2026-10-02 定向）**：agent 的系统提示词须补充知识相关内容，让 agent "知道有知识库、会用、会写、会沉淀"：

- **能力声明**：知识库存在、召回 tool 的用法与时机（遇到项目问题先召回相关约束/经验）；
- **写作契约**：写知识时遵守 frontmatter schema（摘要/关键词/状态/作者/时间）与**目录层级约定**（最多三层、一级目录 = 域、跨域入共享域目录），不合格条目会被契约校验拒收；
- **抽取时机指引**：何时值得沉淀知识（解决了一个可复用问题、形成了一条约束判断等），自动抽取的判断依据；
- **置信度语义**：召回结果已按置信度排序，agent 可据此权衡采信程度。

归属边界：系统提示词知识段的组装属**知识插件**（随产品交付）；产品负责提供**契约内容源**（frontmatter schema、域层级约定、召回能力说明作为宿主能力面的自描述文档），知识插件将其编入提示词——产品不注入会话，只出契约。知识插件独立于 forge 插件（SDD 管线），不随管线演进绑定。

### 流程承载（方向锚点，待定）

**创作归技能**（v1 实施）：提案/PRD/技术方案/测试用例等产物内容，由各角色与 agent 会话经技能产出，产物存储维持既有归属（默认仓内、应用只读）。**流程归产品**（待定方向）：流程状态机（阶段门/评审/批准/回退/待办轮转）未来演化为产品能力——各角色（需求方写提案、PM 写 PRD 画原型、研发做方案、测试写用例）经产品协作、评审、推进流程。desktop **暂定单机产品**；多人协同需联网，属未来命题。forge 插件的独立迭代不得堵塞此路径。

### 存量处置

拉**零代码新分支**，从零开始实现；dsh-forge 主分支历史（M1–M4 文档）保留为教训与参考。**本产品独立于 Claude Code 插件，不提供迁移能力，保持纯粹**——旧世界资产（仓内任务文件、旧插件管线）原地保留不迁移，新旧并行直至旧线自然废弃。

### Innovation Highlights

- **知识资产复利飞轮（核心卖点）**：把研发经验显性化为可管理、可置信、可复利的知识资产——抽取（用户/agent 双路）→ 置信度动态筛选（审核/使用/反馈/衰减四信号）→ 域过滤召回 → 复用再沉淀。对照 Linear/Jira 管协作不管经验资产、AI 客户端管会话不管知识沉淀，本产品占「AI Coding 时代研发流程的知识资产层」交叉位。
- **薄状态层定位**（诚实声明：架构纠偏，非创新）——应用不碰代码仓、不碰文档创作（归技能）、不自动编排 agent；知识域是产品自有的核心域。
- **按资产类型一次划清 SoT**：以「生命周期/复用域/写者」为轴的文档归属分类，替代运行时投影折衷——是对 M2–M4 双层架构的方法论否定。
- **为 forge 而建 + 基础能力沉淀**：产品直接表达 forge 场景语义，零场景中立抽象；通用能力在迭代中按证据沉淀为基础包，未来新场景 = 在基础能力上快速搭建新产品。
- 知识两层（项目级/全局）独立于代码仓，过程资产与代码解耦的思路继承自三分模型，但去掉了应用侧纳管。

## Requirements Analysis

### Key Scenarios（对应原型场景走查 1–9）

- 首用：零配置启动 → 首屏 = 工作台（hero 相位）→ 左栏 ＋ 添加项目（代码区路径 + 文档位置预览 + 知识目录 + 默认召回域；「先 dsh create（幂等）后自家外键」）。
- 日常：左栏切换项目/会话（dock 页签集跟随项目切换，面板状态不打断）；中区发消息 → agent 召回知识（命中卡片附置信度与命中理由，可采纳/忽略/读正文）。
- 知识管理：左栏「知识库」入口 → **整体切换为知识库一等公民视图**（右栏隐藏，状态保留）→ 浏览页签：搜索 / 域树前缀过滤 / 状态 chips + 阈值 / 范围下钻（全部 → 项目 → 会话）/ 卡片网格 / 详情抽屉（元数据编辑对话框经宿主能力面）。
- 统计分析：时间过滤（快捷 chips / 自定义范围）→ KPI → 召回分布逐级下钻（项目 → feature → 会话）→ Top / 盲区 / 反馈质量 / 动词转化 → 自由分析（维度 × 指标）——目的 = 持续迭代提升召回率。
- 召回日志：知识库第三页签查看召回 trace 流（执行点即时记录）；行内元数据 + 展开详情；trace_id/关键词检索；范围下钻同步收窄；空结果轨迹 = 盲区信号。
- 知识 ↔ 会话 / 知识 → dock：引用双入口（当前会话 @预填 / 新会话 hero 草稿）；「在 dock 打开」→ 切回会话视图 + 知识文档页签（页签跟随项目）。
- 会话知识：打开会话 → 「知识召回」tab 查看本会话召回的知识（分组行 / 反馈 / 跳详情）与抽取沉淀；发送消息后事件即时累积。
- 置信度生命周期：抽取落库（pending，中等置信）→ 审核通过提升 → 闲置衰减（时间模拟）；阈值 chip 直观看到过滤；徽章气泡看四信号构成。
- 去重与晋升 / 对账 / 外部修改：合并队列（保留一侧合并）；晋升到全局 + 重定向幽灵卡；移动换域稳定 ID 不变；目录移动失配按 path 找回；外部改动 → 对账横幅 → 重建索引。
- 状态查看：任务三视图（列表/DAG/泳道，feature 绑定）从应用数据库直读；tool 写入即时刷新（无文件扫描、无投影同步）。

### Non-Functional Requirements

- 继承 M1 壳层 NFR（离线自足、进程足迹、可恢复性、无监听端口、三平台分发）。
- 状态读写延迟：任务/看板数据全部来自数据库，首屏无需文件扫描。
- 应用对仓内文件零写入（只读纪律），杜绝"应用改仓"造成的双写。

### Constraints & Dependencies

- **硬约束：dsh 为唯一 agent 运行时**（归零设计、锁定约束——从需求推导而非架构出发）。
- dsh 0.1.x-rc 快速演进：版本锁定 + 显式适配任务策略继承。
- forge 技能（管线）过渡期继续以现有形态运行；新产品侧任务清单/执行记录直接落应用运行时存储（经 forge 插件 tool 半身写入），**不迁移旧仓内文件**（见 §存量处置：不提供迁移能力）。
- 上游 dsh 源码（`Z:\project\github\deepseek-harness`）为唯一权威参考。

## Feasibility Assessment

### Technical Feasibility

中高——壳层/宿主/协议缝技术已由 M1–M4 验证；**除薄宿主 spike（runProfile 直跑）外无未验证技术依赖**，spike 失败有 vendor fallback。风险注记：知识内核（抽取去重 + 契约校验 + DSM 维护 + 动态置信度 + 召回四动词 + 可解释 + 晋升流）是**一整个子系统**，P2 为最大工作量阶段，`/write-prd` 时可再拆子阶段；且单人三线并行（产品 + forge 插件 + 知识插件）进度风险须在里程碑排期中显式权衡。

### Resource & Timeline

单人产品线；零代码分支上按新 PRD/设计/任务管线推进，里程碑划分留待 `/write-prd`。

### Dependency Readiness

无外部 API 依赖；dsh 本地源码齐备；forge 自研可控（新产品侧任务/记录直落应用存储，经 forge 插件 tool 半身写入，无需迁移改造）。

## Scope

> 本总纲的 Scope 定义的是**整个产品线的边界**（宪法级）；各阶段的交付切分见 §演进路书，阶段内细化以阶段提案为准。

### In Scope（产品线边界；阶段切分见路书）

- **零代码新分支**：从零搭建应用（壳 + 原生三区工作台 UI，UX 基线 = M4 原型）。
- 薄状态层数据模型落地：任务清单/执行记录迁入应用运行时存储；任务/feature/提案状态、会话挂接、视图状态入库为唯一 SoT。
- 文档归属模型：注册时选择 proposal/PRD/design 仓内（默认）或仓外；知识两层目录约定；应用侧一律只读引用。
- **知识资产全链路（核心卖点）**：知识库**一等公民视图**（中区整体切换；浏览页签：范围下钻/域树/卡片网格/详情抽屉/frontmatter 编辑；统计分析页签：时间过滤/KPI/召回分布下钻；召回日志页签：trace 流与详情）+ 深度统计分析（P4）；知识 ↔ 会话联动（引用双入口 / dock 知识文档页签）；会话知识召回 tab；**审核工作台**（待审核队列 + 合并队列视图——抽取去重与晋升冲突共用）；抽取（用户触发 + agent 自动）；动态置信度（审核/使用/反馈/衰减四信号，读取时计算）；宿主召回能力（域过滤 + 置信排序 + 使用事件记录 + trace 执行点写入 + 可解释命中理由 + 分层阅读动词 + 会话→域映射）；**知识插件**（随产品交付：召回/写入 tool + 知识技能 + 系统提示词知识段）。
- dsh 会话面板作为中区组件接入（引擎能力复用，不重造）。
- 既有 plugin-forge-workbench 工作台视图与投影层的移除（旧分支收尾，不进新分支）。

### Out of Scope

- SDD 管线的应用原生编排（管线权归 forge 插件 skills 半身；未来独立提案）。
- **流程归产品**（阶段门/评审/批准/回退/多角色协同）——待定方向锚点（见 §流程承载），单机产品先行，多人协同需联网属未来命题。
- forge 插件（技能 + CLI→dsh tool 合一）的封装与分发——独立工程，与本产品并行推进、互不阻塞；本产品只负责暴露宿主能力面（含召回）。
- 文档编辑、导出、wiki 对接、双向同步（应用只读）。
- 深度统计分析（自定义时间选择器、自由分析、盲区/反馈质量下钻——原型 C 组高阶项）——属 P4 打磨阶段交付，不阻塞知识内核。
- 多窗口、拆分面板、深度原生 UI、代码签名（继承既有 Out of Scope；原型亦未实装，聚焦知识链路）。
- 旧分支 M4 遗留项（20 技能/四动词/影子 git/runtime_root）的清偿——随管线归属议题顺延。
