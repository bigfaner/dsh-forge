### Key Decisions
- Guard placement followed the task file plan (new plugin-runtime/ module) instead of consolidating into workbench/ipc/plugins.ts: host-profile (startup projection domain) needs overlay reads, and importing the IPC face from it would invert repos-style layering; ipc/plugins.ts now delegates overlay I/O to plugin-runtime/overlay.ts and re-exports the 2.7 seam contract (PluginEnableGuard/PluginMandatoryError) so existing import paths stay stable. Single write path preserved: writePluginRuntimeOverlay is the only overlay writer and setPluginEnabled its only caller.
- Malformed-vs-violating split: structural malformation (bad JSON / non-object root / unknown keys / missing or non-array disabled) -> ERR_PLUGIN_RUNTIME_STATE + isolate as plugin-runtime.json.corrupt-<ts> (ERR_WORKBENCH_DB backup precedent) + rebuild empty overlay, never blocking startup; schema-valid violations (mandatory names / unknown names / non-string entries) keep the 2.7 strip+log semantics (manifest state wins).
- Strict loader accepts only literal mandatory: true (absent = third-party); false/other values fail loud (ERR_PLUGIN_BUNDLES_CONFIG) rather than half-marking the protected partition.
- forge-workbench manifest entry intentionally NOT added: task 3.2's AC owns both the plugin package and its manifest entry; 3.1 lands the mandatory convention on @deepseek-ai/dsh-base and @deepseek-ai/dsh-web-app only (a placeholder name that cannot resolve from the vendored closure would risk host boot).
- Overlay consumed by host-profile via optional deps.overlayPath (missing/absent = empty overlay = all enabled); main/index.ts passes <userData>/plugin-runtime.json — the same file the setPluginEnabled verb writes.
