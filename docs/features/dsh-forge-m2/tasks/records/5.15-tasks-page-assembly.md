### Key Decisions
- Single-subscriber semantics enforced renderer-side: a WeakMap-keyed refcounted event source (ipc/workbench-events.ts) owns THE one bridge.onEvents subscription; the task-board store's data leg, the page's presentation leg (row highlights + aria-live), and 5.14's overview store all multiplex over it, releasing only at the last detach — without this, a tasks-tab unmount would have killed the overview family's sync pushes (handlers.ts unsubscribe deregisters the whole webContents).
- Coalesce-then-fetch: never fetch per event — pushed batches (already ≤500ms-coalesced main-side) arm a 400ms trailing debounce that fires ONE getTaskBoard. ≤5s budget math: 400ms watcher + ≤500ms push + 400ms client debounce + one SQLite snapshot read + row-level render ≈ 1.3s worst-case; the updating highlight lights at EVENT ARRIVAL (pre-fetch), so perceived freshness = push latency.
- Two counters in the store (revision vs feed): a page-initiated read resolves to its caller and does NOT advance feed, so the view never answers the page's own fetch with a reloadToken bump (which would double-fetch); only store-initiated publishes (event refresh / sync merge) advance feed and trigger the token re-feed, which SERVES the fetched snapshot (zero extra verbs). The sync 重试 falls to the fresh-fetch leg precisely because every published revision was consumed.
- Structural-deletion dock coupling lives page-side: task_updated(structural) keys are marked in handleEvents; a load that settles without the OPEN key bumps the dock's reloadToken (new TaskDetailPanel prop) — the re-read rejects on the deleted snapshot row and the dock's existing error card shows (ui-design 焦点任务被删且侧板开启 → 侧板转错误态). Keys proven alive retire their marker (structural ≠ deleted); markers of absent keys persist so a mid-flight event can't be lost to a racing settle.
- Sync events merge into the board DTO's sync projection (toolbar light moves without a board round trip); a sync event arriving mid-read is re-applied over the settle (strictly fresher), while pre-read events never survive the next read's authoritative DTO.
