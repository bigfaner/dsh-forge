### Key Decisions
- Inline-constant carrier chosen over a build step for the schema DDL (task 2.1 offered both): plain TS import graph, packaged app needs no resource file; store/schema-v1.sql remains the projection record and workbench-store.spec.ts enforces constant<->file sync via a drift test.
- The two PRAGMAs from design/schema.sql are intentionally NOT in the v1 DDL: they are connection-level settings applied by db.ts on every open (foreign_keys does not persist in the file; journal_mode cannot change inside a migration transaction). Deviation declared in schema-v1.sql header.
- process.features.sqlite is used only as a fast negative hint (observed undefined on Node 24.x builds that do ship node:sqlite); the authoritative probe is the dynamic import plus an in-memory trial open, matching the design's '试开库' wording.
- Corruption is classified by SQLite errcode (26 NOTADB, 11 CORRUPT) or message pattern; non-corruption open/migration failures (e.g. a newer schema_version from a future build) stay fatal ERR_WORKBENCH_DB and never wipe user data.
- v1 migration runs inside BEGIN IMMEDIATE with clear-then-write for the single schema_version row; WAL/-shm siblings travel with the corrupt backup because a stale live -wal would be recovered on top of the rebuilt database.
