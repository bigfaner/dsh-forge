# 技术方案评审（review-tech）

tech-design 生成后、breakdown-tasks 前。核心问题：**这份方案是否以最优雅的方式达成了需求？**字面逻辑完整性是及格线（见下），不是评审目的。只出报告不改设计，返工权归 tech-design。

## 执行机制：独立 subagent

- 主会话只做两件事：**组装简报**（评审对象与对照正本路径；不含设计讨论过程与预期结论）与**转呈结果**。
- subagent 不继承主会话上下文，结论以自己读到的文档与代码为据；报告落盘 `design/review/report.md`（feature 目录相对路径），主会话不改报告，只做后续处置。

## 评审四问

1. **真需求对齐（XY 问题）**——方案解的是 PRD 的真问题吗？逐个 In Scope 条目对照：直击根因还是在症状上贴补丁？手段是否被当成了目的？
2. **最短路径**——存在更简单的达成方式吗？逐块追问：官方/既有同功能机制是否被充分复用；能否整块删除某个子系统、层、抽象而需求仍成立；既有能力组合是否已足够。
3. **改动收敛**——改动面最小吗？新增的机制、文件、依赖各有不可替代的理由吗；抽象层是为当下需求还是想象的未来；对宿主与上游官方包的改动是否只落在官方扩展点与最小装配处。
4. **结构优雅**——职责划分自然（一个模块一个变更理由）；依赖方向指向稳定方；无重复实现（两处做同一件事、与既有结构平行重复）；命名与既有词汇一致。

## 及格线

不过即 Blocker，但不构成评审的主要产出：

- **可行性事实核验**：引用的包、官方扩展点、服务、API 真实存在且语义如所述（读 lockfile/源码验证）；点名的改动文件在仓库存在；测试策略与实际测试流程吻合。
- **流程闭环**：Coverage Map 双向核对（每条 AC 有设计元素、无孤儿）；关键流程的失败分支有明确处理；跨模块调用定义了失败时的行为。

## 输出与处置

报告（无 `doc_kind`，不得虚构注册；含 `created` frontmatter）问题三级：

| 级别 | 判据 | 处置 |
|---|---|---|
| **Blocker** | 更优雅的路径明确存在且改动可承受 / 真需求错位 / 及格线不过 | 返工 tech-design 并重新注册，重评清零才放行 breakdown-tasks |
| **Question** | 优雅性权衡可辩，agent 无法单方裁定 | 交互语境 `ask_user_question` 裁决；派发语境呈报于任务输出 |
| **Note** | 不阻塞的改进建议 | 留档 |

- 报告主体 = 四问的结论与证据（文件:行 / 包版本 / 更简单方案的具体内容）；及格线问题一句话带过。
- 「更优雅」的断言必须给出**具体替代方案**（删什么、用什么、为什么仍满足全部 AC），不接受空评。
- 放行判据 = Blocker 清零且 Question 全部有裁决；报告尾记录放行结论与裁决清单。
- 交互语境：Blocker 清零后向用户呈报放行结论，经确认进入 breakdown-tasks。派发语境（doc-review 任务）：worker 即独立上下文直接执行，无 Blocker 按简报结算。

## 方法论速查

- **XY 问题**：先验「要解的是 X 还是 Y」——手段被当目的即错位。
- **奥卡姆剃刀**：候选中假设最少者胜；为想象的未来加抽象层是负担。
- **5 Whys**：对每个设计决策追问五层「为什么需要」，答不到需求层 = 可删。
- **恶魔代言人**：对每个 ADR 站在弃选候选立场反驳一次，并替「什么都不做」辩护一次。
