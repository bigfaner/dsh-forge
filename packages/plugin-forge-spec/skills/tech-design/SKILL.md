# 技术设计（tech-design）

## 前置条件

| 工件 | 缺失时 |
|---|---|
| `prd/prd-spec.md`（注册为 `prd-spec`） | 先跑 `write-prd` |
| `ui/ui-design.md`（特性有 UI 时） | 先跑 `ui-design` |

## 状态层纪律

设计工件落盘后即用 `upsertFeatureDoc` 注册（机制语义见 forge:spec 系统提示段）。路径按 `<slug>` feature 目录相对约定（`design/<name>`）；存储布局见 forge-pipeline 系统提示段「文档位置/目录树」。含 mermaid 图的工件自检纪律：图写完 → `validateMermaid` 自检 →再 `upsertFeatureDoc` 注册。

| 工件 | 注册方式 |
|---|---|
| 技术设计 | `upsertFeatureDoc` `doc_kind: tech-design` |
| ER 图 | `upsertFeatureDoc` `doc_kind: er-diagram` |
| SQL schema | `upsertFeatureDoc` `doc_kind: sql-schema` |
| 页面地图（有 UI 时） | `upsertFeatureDoc` `doc_kind: page-map` |

`api-handbook.md` / `cli-handbook.md` / `screen-map.md`（下方设计手册）**没有注册 kind**——它们是 gen-contracts/gen-test-scripts 消费的盘面工件，不得虚构注册。

## 意图适配

读 brainstorm 提案文档的 `intent` frontmatter（`<slug>` proposal 目录相对约定，见系统提示段目录树）；缺失 → `new-feature`。

- `new-feature`：全量设计——所有段落；用户故事即 AC 清单。
- `enhancement`：聚焦内部架构；改进目标替代用户故事作清单；手册/ER 仅覆盖信号触发。
- `refactor` / `cleanup` / `fix`：仅内部架构（模块重组、依赖调整、行为不变量、回归风险）；无 ER 图、无用户故事；PRD 的 Verification Criteria 即 AC 清单。
- `doc`：极简——改什么、为什么；无架构/接口/数据段。

## 硬性段

设计文档**必列**两段，任何意图不豁免：

- **改动范围**：受影响的包/模块/文件（包粒度），具体路径。
- **影响范围**：下游消费方（接口调用者、依赖本包的模块、契约/测试面）与运行时影响（接口形态、构建、schema），未触及的写"无"并说明判据。

## 决策分级与确认纪律

设计期决策分两级，判据 = 换选项是否导致返工或影响下游契约：

- **选型级**（技术栈、架构决策 AD、交互方式、持久化/数据载体、测试策略主径）：
  - 交互语境：权衡成稿后必须经 `ask_user_question` 呈候选确认（推荐项排首 + 每项一句话权衡），用户明示确认后才写入设计文档；用户另择候选时补记其理由。未确认的选型级决策不得定稿、不得进入实现。
  - 派发任务语境：简报已裁决的依简报决断并留痕；简报未覆盖的选型级决策 → `submitTask` `result=blocked` 上报，不得擅自定。
- **实现级**（命名、文件组织、局部惯用法）：agent 决断并在文档留痕即可，不打扰用户。

## 图示与文档拆分

- **图优先**：架构、核心逻辑、关键业务流程一律优先用 mermaid UML 图描述（架构 = flowchart/component、核心逻辑 = stateDiagram、业务流程 = sequenceDiagram/flowchart）；文字只做图说不清的约束、判据与理由，不复述图内信息。
- **按模块拆分**：功能复杂（多模块/多子系统）时按功能模块拆分设计文档（`design/<module>-design.md`），`tech-design.md` 保留全局总览（架构图 + 决策索引 + PRD Coverage Map）并以相对链接引用子文档；子文档无 `doc_kind`，不得虚构注册。

## 技术栈选型步骤

1. **候选并列**——每个决策点（框架/库/语言特性/工具）列出 ≥2 个候选，不预设答案。
2. **评估**——按 PRD 非功能约束与项目现状（既有依赖、团队约定、维护成本）构建**权衡矩阵**：行=候选，列=约束维度（性能/兼容/生态/迁移成本…），格内定性打分。
3. **决策与理由留存**——写入设计文档：选中者、矩阵结论、放弃候选的原因（一句话即可，但必须留痕）。写入前过确认纪律（选型级决策）。

## 技术架构决策

架构级决策（分层、事件模型、持久化策略等）逐条成段，ADR 风格：**候选并列 → 权衡（矩阵或逐维对比）→ 决策记录，含弃选原因**。留痕判据：三个月后新人只读文档能回答"为什么当时不选 X"。决策记录写入前过确认纪律（选型级决策）。

## 模块/包设计

新模块或模块重组时显式成段：

- **能力边界**：本模块管什么、不管什么（越界即依赖方向错误的前兆）。
- **职责划分**：单一职责；一个模块一个变更理由。
- **依赖方向**：依赖指向稳定方（领域 → 接口 → 基础设施），禁止环。
- **对外接口**：公开 API 面（导出符号/入口函数），内部细节不外泄。

## 跨模块/服务交互契约

brainstorm 已识别交互面（谁与谁、哪些流程、边界在哪）；此处精确设计**三要素**：

1. **流程时序**：跨模块流程配 mermaid `sequenceDiagram`（参与方、消息序、失败分支）。
2. **交互方式**：同步调用/异步事件/消息队列等，写明选型理由（一致性要求、耦合容忍、失败语义）——此为选型级决策，过确认纪律。
3. **契约数据模型**：请求/响应/事件的 schema（字段、类型、必填性），与 Interfaces 段衔接，不另起炉灶。

## 工作流

1. **读 PRD**（含用户故事或其意图替代物）；摘录非功能约束——它们是选型的输入条件；提取 `db-schema` frontmatter 值供 DB 分支。
2. **探索上下文**——既有架构与决策文档（`docs/ARCHITECTURE.md`、`docs/decisions/`）、历史特性的业务规则与约定、包管理器文件的现有依赖、源码目录的既有模式。
3. **识别决策并分级**——架构适配、接口、数据模型、依赖、错误处理、测试策略、安全、本地开发；逐项按「决策分级与确认纪律」定级，选型级决策进入确认流程。
4. **逐节起草并确认**——概述 / 架构图 / 技术栈选型 / 架构决策 / 模块设计 / 交互契约 / 接口 / 数据模型 / 错误处理 / 测试，按意图取用。确认粒度：选型级决策逐点确认（`ask_user_question`），叙述性内容整稿确认；DB 分支同下。逐节自检并产出命名节**PRD Coverage Map**（breakdown-tasks 的核对输入）：每条 PRD AC 映射到设计元素；跨层数据流已测绘；集成点已规格化；每节可直接拆任务。
   - **DB 分支**（`db-schema: "yes"`，new-feature）：随数据模型段生成 `er-diagram.md`
     + `schema.sql`，作为独立评审单元呈现——未明示批准不得推进。`er-diagram.md` 图外必附两说明：**实体说明**（每实体一行职责）与**关系说明**（基数 1:1/1:N/N:M、外键方向）。**索引纪律**：非必要不加（判据 = 明确的查询/守卫路径需要）；优先联合索引覆盖多条查询路径，避免单列索引堆叠。
5. **落盘并注册**——`design/tech-design.md` 必出；DB 分支出 ER + schema；设计手册按交互形态产出：`api-handbook.md`（API 交互）、`cli-handbook.md`（命令行交互）、`page-map.md`（Web UI）、`screen-map.md`（移动 UI）——形态从 PRD UI 功能的平台/交互方式推断，不许猜；判定属选型级决策，过确认纪律。monorepo 下按模块归属分别产出（模块归属判据与测试链统一：目标模块 = workspace 包/应用目录，从 PRD UI 功能落位推断；含糊 → 问用户或推导并记录）。手册带 `created` frontmatter 时间戳供下游新鲜度检查。
6. **决策留存**——重大决策写在设计文档内；归档到 `docs/decisions/` 是本技能之外的长期归档动作，认为有必要时向用户提议，不擅自执行。

## 方法论速查

- **DDD 限界上下文**：按业务边界切模块而非按技术分层——上下文地图即依赖方向依据。
- **TOC 约束理论**：先找瓶颈（最不确定/最高风险处）先设计，局部优化不救全局吞吐。
- **奥卡姆剃刀**：能简单则简单——候选中假设最少者胜，避免为想象的未来加抽象层。
- **预验尸**：动工前假设"已失败"，倒推最可能的死因并写入设计的规避措施。
- **FMEA**：按 严重度×发生度×可检测度 排故障模式，高风险项必须有设计侧对策。
- **权衡矩阵**：候选×约束维度打分表——把取舍从"我觉得"变成可审计的结论。
