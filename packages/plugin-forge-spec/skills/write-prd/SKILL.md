# 撰写 PRD（write-prd）

从模糊需求出发，经协作对话收敛为清晰的 PRD（产品需求文档）。作用于已有的 feature 容器。

**核心原则**：动手编码之前，先澄清"做什么"与"为什么"。

## 状态层纪律

每份文档落盘后即用 `upsertFeatureDoc` 注册（状态层机制语义——事实源/单调推进/返工重注册——见 forge:spec 系统提示段）。路径按 `<slug>` feature 目录相对约定（`prd/<name>.md`）；存储布局见 forge-pipeline 系统提示段「文档位置/目录树」。

| 文档 | 注册方式 |
|---|---|
| PRD 规格 | `upsertFeatureDoc` `doc_kind: prd-spec` |
| 用户故事 | `upsertFeatureDoc` `doc_kind: user-stories` |
| UI 功能 | `upsertFeatureDoc` `doc_kind: ui-functions` |

注册调用形态（参数 snake_case；`rel_path` 仓库相对路径、正斜杠，按上方相对约定）：

```
upsertFeatureDoc { feature_slug: "<slug>", doc_kind: "prd-spec", rel_path: "docs/features/<slug>/prd/prd-spec.md", summary: "<一句话>" }
```

先写文件再注册（或先注册后立刻补写——行可能短暂悬空，但绝不留下未注册的产出文档）。含 mermaid 图的文档自检纪律：图写完 → `validateMermaid` 自检 → 再 `upsertFeatureDoc` 注册。没有 manifest 也没有索引要维护——状态层已取代二者。

<HARD-GATE> PRD 定稿并获用户批准之前，不得写任何代码、搭任何项目骨架或采取任何实施动作——先呈现 PRD，先拿批准。 </HARD-GATE>

<HARD-RULE> 不做技术选型：允许描述非功能约束（性能、平台、兼容性、安全/合规）；禁止点名框架、语言、数据库、库或架构模式——那些属于 tech-design 技能。判据："要达成什么效果"可以写，"用什么工具实现"不可以写。 </HARD-RULE>

## 意图管线

若 brainstorm 提案文档存在（`<slug>` proposal 目录相对约定，见系统提示段目录树），读其 `intent` frontmatter；缺失或为空 → 按 `new-feature` 处理。意图决定格式：

| 意图 | PRD 格式 | 用户故事 | UI 功能 |
|---|---|---|---|
| `new-feature` | 完整版 | 是 | 是（仅 UI 交互） |
| `enhancement` | 背景 + 目标 + 验收管线 | 否 | 有信号才写 |
| `refactor` / `cleanup` / `fix` | 仅规格（下方三个必填字段） | 否 | 否 |
| `doc` | 极简（标题 + 目标 + 范围） | 否 | 否 |

内容生成阶段探测到的**覆盖信号**只增步骤、从不删减，且相互独立叠加："用户可见行为"/ UI 变更信号启用用户故事 + UI 功能；否定语境中的跳过信号不触发；触发时注记（`<!-- Override: ... enabled by signal "..." -->`）。

**仅规格必填字段**（refactor/cleanup/fix）——替代用户故事，作为 tech-design 的信息载体：

- **改动范围**：受影响的模块/文件/包（具体路径）
- **约束**：不得破坏的行为不变量
- **验收标准**：回归验收——如何在不引入回归的前提下确认成功

## 验收标准形状与取证纪律

### AC 分档：强制域 / 豁免域

AC 的取证义务按**交付物性质**分档，不随 AC 文案是否「提到 UI」漂移：

| 域 | 判据 | AC 要求 |
|---|---|---|
| 强制域 | 交付物含**运行期装配面**（进程、网络端点、真实调度/时钟、对外部系统/硬件的真实副作用） | 必含真机端到端取证条目，写明**取证方式 + 取证环境**；单测全绿不算完成 |
| 豁免域 | 纯逻辑（纯模型/算法/状态机，单测可判）、纯文档/规格（评审可判） | 无真机取证要求 |

- 七类常见强制域示例：UI、API、CLI、TUI、Desktop、Web server、MQ 事件发布/订阅——**清单非穷尽**，唯一判据是运行期装配面；清单外类型（浏览器扩展、移动端 App、定时任务/批处理、数据库迁移/存储过程、RPA 脚本等）命中判据同样入强制域。
- **SDK/库边界**：库本体无自有运行期装配面（装配由消费方承担）→ 豁免域；库自带子进程/网络/线程等真实副作用时回到强制域。
- **多类交叉**：同一交付物落入多类时强制义务不变；取证环境按**主交付面**（最终消费者直接感知行为的运行面）选取，就高不就低（如 Web server∩API 按完整真实服务端到端取证）。
- 依据正本：`docs/conventions/external-dependency-verification.md`（AGENTS 1.4）。

### 取证方式的确定顺序与前置检测

确定取证方式按三级顺序递进（agent 自主，不轻易问人）：

1. **项目既定程序**——查项目 `AGENTS.md` 与知识文档（含 `.knowledge/` 沉淀），既定取证程序/判例直接复用；
2. **自主检索核销**——无既定程序时，检索并核销相关知识自行确定取证方式；
3. **询问用户**——当且仅当不确定时才问。

取证执行前必须**检测取证环境可用性**：所需软件是否安装、环境是否允许（网络/权限/凭据）。不可用时显式报告环境缺口并以 blocked 结算，**禁止静默降级为模拟取证**。

### 视觉 AC 基准

- 视觉 AC 基准 = **目标产品的既定视觉基准**（该产品自身的设计系统与实机形态）。
- mockup / ASCII 线框只当**布局草图**，不充当验收基准——逐位对照的对象是目标产品实机形态，不是 agent 自产图。

### 待用户裁决清单（条件强制段）

- 涉 UI/交互面的 PRD **必须**含「待用户裁决清单」段：列出微文案、布局终态、触屏交互词汇等规格中不存在、**只有用户能判**的决策点；无决策点则写「无」。
- 非 UI 面的 PRD 无此段，不判缺陷。

### 正例判例（super-composer）

写取证条目、裁决清单与归档时参照以下正例形状：

- **真机取证结算门 AC**：真实宿主 + 真实 dist 驱动走查、样式逐项自检、截图归档 `walkthrough/`（判例 = super-composer AC12）。
- **用户裁决台账段**：裁决逐条落档、可追溯（判例 = super-composer §6-§8 形态）。
- **walkthrough 分批归档**：按批次/场景子目录留盘，验收记录与实现同步产出。

## 图示要求

### PRD 用例图（范式 + 分档）

- **范式**（`flowgraph` 扮演者 → 用例形，多角色/多流程特性照此内置）：

  ```mermaid
  flowgraph LR
    管理员((管理员)) --> UC1([注册工作区])
    管理员 --> UC2([评审提案])
    开发者((开发者)) --> UC2
    开发者 --> UC3([派发任务])
    UC2 -.扩展.-> UC4[升级为远征]
  ```

- **分档**：多角色或多业务流程的特性**强制**内置用例图；单一角色、单一流程的简单特性允许纯文字描述（一段话列清谁做什么即可），不硬凑图。
- 流程图：`new-feature` 的业务流程**必须**配 mermaid flowchart（工作流第 5 步）。

### prd-ui-functions 写作要求

- **布局**：关键页面配 ASCII 线框（围栏代码块内画区块布局：导航/主区/操作位）；仅限关键页，次要页面文字描述位置即可。
- **交互**：多步交互配 mermaid flowchart（状态流转复杂时用 `sequenceDiagram`）表达页面/动作流转，文字只做补充。

## 方法论速查

- **JTBD**：用户"雇佣"产品完成什么任务——目标句式"当…时，我要…以便…"，防功能清单偏离真实动机。
- **KANO**：区分基本/期望/兴奋需求——验收基线保基本，兴奋项标注防范围膨胀。
- **赫茨伯格**：保健因素（缺失即不满）与激励因素（具备才满意）分开列——非功能约束多属保健项。
- **用户故事地图**：按用户活动轴排列故事——先走通端到端脊梁，再向下切片迭代，防只按功能块平铺。

## 工作流

1. **探索上下文**——读提案（可选输入）、相关 feature 文档与近期工作。若仓库维护 web 站点地图（`docs/sitemap/sitemap.json`）且请求触及既有页面，将其作为业务级页面清单读取；不要读架构/决策文档来牵引需求——技术约束不属于 PRD。
2. **评估范围**——多个独立子系统 → 请用户先拆分。
3. **提出澄清问题**——一次一个，优先选择题；焦点随意图变化（new-feature 问角色/目的/约束；仅规格问改动范围/不变量/验收）。派发任务语境（无交互用户）下，依任务简报自行决断并记录假设，不做阻塞等待。
4. **提出方案**（仅 `new-feature`）——2-3 个业务方案含取舍与推荐；不做技术选型。
5. **分节呈现**——背景（缘由、用户、干系人）→ 目标（尽可能量化）→ 范围（In/Out）→ 流程（业务流程；new-feature 必配 mermaid 流程图）→ 功能规格（引用 ui-functions 文件）→ 非功能注记。逐节获取批准。
6. **撰写文档**——按上方意图表执行。
   - PRD 规格：frontmatter 必带 `db-schema: "yes" | "no"`（特性是否引入/变更持久化数据模型——tech-design DB 分支的判定输入）。
   - 用户故事：仅 new-feature（或"用户可见行为"覆盖信号；当所有 In Scope 条目都指向不可编译工件时不写）。背景中每个角色 ≥1 条故事；动作具体；每条故事带可客观核验的 Given/When/Then 验收标准。
   - UI 功能：仅当特性有 UI 交互。含每项功能的落位（`new-page` vs `existing-page:<route>`）与导航架构一节，并遵守上方"prd-ui-functions 写作要求"（ASCII 线框限关键页 + mermaid 交互图）。
7. **注册每份产出文档**——经 `upsertFeatureDoc`（见上表）；返工重注册语义见状态层纪律节所引 forge:spec 系统提示段。
8. **自检**——背景各维度覆盖；目标尽量量化；范围边界显式；验收标准可核验；覆盖信号已注记；无范围外内容渗入；强制域 AC 含真机取证条目（取证方式 + 取证环境）；涉 UI/交互面的含「待用户裁决清单」段（无决策点写「无」）；视觉 AC 基准为目标产品既定视觉基准。
