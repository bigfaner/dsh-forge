# 修缺陷（Fix Bug）

系统化缺陷修复流程：**理解 → 复现 → 失败测试 → 修复 → 验证 → 提交**。

核心原则：**失败测试证明 bug 在场之前，不碰任何产品码。**

## 编码纪律

- **先想后写**：动手前用自己的话复述 bug 与疑似根因，用证据检验诊断——不轻信第一个
  看似合理的解释；根因含糊就继续排查。
- **最小修复**：只修坏掉的东西。不做投机改动、不做"顺路"优化、不重构；琐碎修复
  （错字、配置）自行裁断是否需要完整分析。
- **外科手术式改动**：只改失败路径上的代码。不碰邻近代码、不重排无关行、不顺手整理
  切向逻辑。范围边界 = 失败代码路径。
- **目标导向**：定义清晰可验证的成功条件——修复前失败的那些测试、修复后必须通过。
  实现后确认条件达成，未达成就迭代。

## 四条硬规则

<HARD-RULE>
1. **复现失败即停**：bug 无法在当前代码库复现 → 停止流程（见 Step 2 HARD-GATE），
   并仍须调用 `resolveBug` 将已登记的记录回填为 unresolved（附原因）。
2. **失败测试先行**：产品码改动之前，测试必须**因这个 bug 而失败**。修复前测试就通过
   = 测试没有捕获 bug，改测试直到它因正确的原因失败。
3. **质量门四门序列**：compile → fmt → lint → unit-test，严格顺序、首败即停。
   具体命令由你根据本仓库实际工具链自行决策——**禁止机械套用固定配方**；任何门失败
   都不得进入提交。
4. **原子提交**：修复与测试必须同入一个原子提交；提交信息含一句 Root cause 注记
   （为什么发生，而不只是改了什么）。
</HARD-RULE>

## 输入语义

用户调用时通常携带两类信息（散文表述，不作机械参数解析）：

- **缺陷描述**：报错信息、issue 编号或一段现象描述——缺席时在 Step 1 排查中交互补齐。
- **范围提示**：受影响的模块/包路径——缺席时自行探测（从症状关键词与栈追踪定位）。

## Step 1: 理解 bug

动任何代码之前收集全部上下文。

**项目规范与惯例搜集（义务，手段不限）**：从 bug 描述、受影响文件与范围推断相关领域，
搜集本项目的规范、惯例与既有决策——知识库检索、`AGENTS.md`、`docs/` 等均可，**不强制
特定 skill 或工具**。无相关规范时明确说明后跳过。

**收集**：bug 描述 / 报错信息 / 栈追踪；复现步骤（来自 issue 或用户）；期望 vs 实际
行为；受影响版本 / 提交（未知时查最近提交历史）。

**定位爆炸半径**：用仓库内检索工具（grep/glob/read 等，按你环境实际具备的为准）找
症状相关文件，查可疑文件的变更历史。

**产出 Bug Summary**（继续之前必须成文）：

```
Bug:       <哪里出了问题>
Trigger:   <触发该问题的确切步骤或输入>
Expected:  <正确行为>
Actual:    <观察到的行为>
Suspected: <疑似位置 file:line 或模块>
```

**落库（第一阶段）**：Bug Summary 成文后立即调用 `recordBug` 登记——提交
summary（一句话 ≤50 字）+ 五字段 + 可选错误类型标注；记录返回的 bug_id，
Step 6 回填时引用。身份、会话与仓库态由工具自行解析，**不要手填**。

---

## Step 2: 复现

在当前代码库确认 bug 可复现，然后才写任何测试。

- 先跑基线测试套件，确认全绿（无既有失败掩盖 bug）。
- 在基线之上重现 bug，把确切复现步骤记录下来。

<HARD-GATE>
无法复现 → **STOP**。不得为未确认的 bug 写测试或改代码。向用户报告排查发现，
并调用 `resolveBug`（outcome=unresolved，附 unresolved_reason——写明停机原因，
通常即 Step 1 排查结论）。流程到此为止。
</HARD-GATE>

---

## Step 3: 写失败测试

写出**因 bug 而失败、修复后通过**的测试——这是修复有效的证明。

**单元测试**：找到离缺陷代码最近的测试文件（沿本仓库既有测试布局惯例），加一个聚焦
用例。命名描述错误行为，如 `bug: 输入为空字符串时返回 null`。

运行单元测试——**修复前必须失败**：

<HARD-RULE>
修复前新测试就通过 = 测试没有捕获 bug。修改测试直到它因正确的原因失败。
</HARD-RULE>

**表面级测试**：仅当 bug 在 API / CLI / UI / mobile / TUI 表面可观察时补加——放入
对应 surface 的旅程测试目录，同样修复前必须失败。纯内部缺陷不需要。

---

## Step 4: 修复

失败测试就位后，实现最小修复。

- 恪守编码纪律——最小修复与外科手术式改动定义范围边界。
- 根因在依赖里时，记录之并施加最小 workaround。

**Root cause 注记**：写一句到代码注释或提交正文：

```
// Root cause: <为什么会发生，而不只是改了什么>
```

---

## Step 5: 验证（质量门）

执行四门序列（硬规则 3）——**compile → fmt → lint → unit-test**，严格顺序、首败
即停：

| 门 | 失败处置 |
|---|---|
| compile | 修复后重跑 |
| fmt | 非阻断警告，按提示格式化 |
| lint | 自修（至多 1 次重试），仍败 → blocked |
| unit-test | 修复后重跑 |

Step 3 写了表面级测试的，一并运行。验证清单：新测试全过；既有测试零回归；构建成功
（如适用）。

<HARD-GATE>
任何既有测试新失败 → 不得进入提交。先排查是否修复引入了回归。
</HARD-GATE>

---

## Step 6: 提交 + 回填

**原子提交**：修复 + 测试同入一个提交。提交信息格式：

```
fix(<scope>): <错在哪、现在对了>

Root cause: <一句话>

Fixes: #<issue 编号>（如适用）
```

**立即捕获 commit_hash**：提交完成后马上 `git rev-parse HEAD`（或等价命令）记下
提交哈希——这是并发安全锚，晚一步并发提交就取错。**落库（第二阶段）**：随即调用
`resolveBug`（outcome=fixed，提交 bug_id + commit_hash）；worktree/branch、修复者
与修复会话由工具以 hash 为锚反查，不要手填。

**输出摘要**（完成后报告）：

```
Bug Fix Summary
───────────────
Bug:     <描述>
Fix:     <改动文件>
Tests:   <N 个单元测试> + <M 个表面级测试>
Result:  全部通过 ✓
Commit:  <hash>
```

---

## 常见陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 写失败测试之前就修 | 永远测试先行 |
| 修复前测试就通过 | 测试没捕获 bug——改测试 |
| 修的比 bug 多 | 只做最小修复；清理另开任务 |
| 用户可感知的 bug 不加表面测试 | 至少补一个表面级冒烟测试 |
| 修复与测试分开提交 | 一个原子提交：fix + tests 在一起 |
| 提交后拖延回填 | 提交→捕获 hash→resolveBug 一气呵成，零并发窗口 |
