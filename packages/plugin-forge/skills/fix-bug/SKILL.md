# 修缺陷（Fix Bug）

流程：**理解 → 复现 → 失败测试 → 修复 → 验证 → 提交**。

核心原则：**失败测试证明 bug 在场之前，不碰任何产品码。**

## 硬规则（全流程停机线；一条一行，细则见所指步骤）

<HARD-RULE>

1. 失败测试在场之前，不碰产品码。
2. 无法复现即停，仍须回填 unresolved。
3. 质量门四序首败即停，禁套固定配方。
4. 修复与测试原子提交，落地即回填台账。

</HARD-RULE>

**条款归属约定**：每条规则只在一处保有正本，他处仅指针引用。历史案例细节不进本文——先进复盘文档，抽象为不含专有名词的原则后方可回灌，且只进一个章节。

## 输入语义

- **缺陷描述**：报错信息、issue 编号或一段现象描述——缺席时在 Step 1 排查中交互补齐。
- **范围提示**：受影响的模块/包路径——缺席时自行探测（症状关键词与栈追踪定位）。

---

## Step 1: 理解 bug

动任何代码之前收集全部上下文。

**收集**：bug 描述 / 报错 / 栈追踪；复现步骤；期望 vs 实际；受影响版本 / 提交（未知时查最近提交历史）。同步搜集项目规范与惯例（知识库检索、`AGENTS.md`、`docs/` 等，手段不限）。

**定位爆炸半径**：检索症状相关文件，查可疑文件变更历史。

**承重假设核销（唯一正本）**：列出修复设计依赖的全部跨模块/跨环境假设，逐条以源头证据（上游源码、宿主实现、实测输出）核销。本仓测试通过不构成核销。核销不了的假设 = 方案未定，不得进入 Step 4。

**产出 Bug Summary**（继续之前必须成文）：

```
Bug:       <哪里出了问题>
Trigger:   <触发该问题的确切步骤或输入>
Expected:  <正确行为>
Actual:    <观察到的行为>
Suspected: <疑似位置 file:line 或模块>
```

**落库（第一阶段）**：Bug Summary 成文后立即调用 `recordBug` 登记——summary（一句话 ≤50 字）+ 五字段 + 可选错误类型标注；记录返回的 bug_id，Step 6 回填时引用。身份、会话与仓库态由工具自行解析，不要手填。

**复发挂链（recurrenceOf，可选）**：诊断判定疑似同一问题复发时，先确认前驱 bug_id——优先用派发简报注入的链候选，详情存疑再 `getBug` 深查（主 agent 侧亦可用 listBugs 检索候选）——然后 `recordBug` 以 recurrenceOf 指向前驱 bug_id 挂链；**首次发生不填**。挂链凭 agent 判定 + 显式引用，不做自动匹配；指向不存在的 bug_id 会被拒写。

---

## Step 2: 复现

先跑基线测试套件确认全绿（无既有失败掩盖 bug），然后在基线之上重现 bug，记录确切复现步骤。

**复现的通用定义（唯一正本）**：复现 = 在与现场**同成因**的条件下重现问题；仅重现表象（相同报错文本、相同截图像素）不算。二手/远程事故：修复结论依赖的每个环境事实（资源实存性、权限、平台、执行上下文）先向报告人核实或就地取证；核实不了的，收口症状面、如实附原始证据（如错误码原样），并在 Bug Summary 标注「成因未定」。

<HARD-GATE> 无法复现 → STOP。不得为未确认的 bug 写测试或改代码。向用户报告排查发现，并调用 `resolveBug`（outcome=unresolved，unresolved_reason 写明停机原因，通常即 Step 1 排查结论）。流程到此为止。 </HARD-GATE>

---

## Step 3: 写失败测试

写出**因 bug 而失败、修复后通过**的测试——修复有效的证明（先行禁令见硬规则 1）。

**单元测试**：找离缺陷代码最近的测试文件（沿仓库既有测试布局），加聚焦用例，命名描述错误行为（如 `bug: 输入为空字符串时返回 null`）。运行——修复前必须因正确的原因失败；修复前就通过 = 测试没捕获 bug，改测试。

**E2E 测试**：仅当 bug 在 E2E 可观察（API / CLI / UI / mobile / TUI 入口）时补加——放入对应入口的旅程测试目录，同样修复前必须失败。纯内部缺陷不需要。

---

## Step 4: 修复

失败测试就位后，实现最小修复：只修坏掉的东西，不做投机改动与顺路重构，范围边界 = 失败代码路径。先用自己的话复述根因并用证据检验，不轻信第一个看似合理的解释。

**结论强度 ≤ 证据强度（唯一正本）**：断言不得强于证据——由错误码、启发式或未核销假设推出的结论，要么降格为猜测（附原始证据），要么升级呈报。

脆弱面（命中任一 → 呈报「症状级 vs 根治级」两案，根治级常涉契约面/持久化变更）：

1. 启发式重建未持久化的事实；
2. 易变字段（标题/显示名/标签）作判别键；
3. 对上游/环境行为打补丁。

依赖内根因未命中脆弱面 → 记录后径直最小 workaround。

**同 bug 再报**：先逐条复核上一修复的承重假设是否仍成立，再开新排查。

**根因自检（提交前最后一问）**：测试通过只证症状消失。撤掉本修复，同成因是否会换路径复发？——能答「不会」并指出根因诞生地（坏事实在哪产生、为何未被显式决定），才算定根；答不出或答案是「会」→ 按脆弱面呈报症状级 vs 根治级，不得径直提交。

**Root cause 注记**：写一句到代码注释或提交正文——`// Root cause: <为什么会发生，而不只是改了什么>`。

---

## Step 5: 验证（质量门）

四门序列（硬规则 3），严格顺序、首败即停：

| 门 | 失败处置 |
|---|---|
| compile | 修复后重跑 |
| fmt | 非阻断警告，按提示格式化 |
| lint | 自修（至多 1 次重试），仍败 → blocked |
| unit-test | 修复后重跑 |

Step 3 写了 E2E 测试的一并运行。验证清单：新测试全过；既有测试零回归；构建成功（如适用）。

<HARD-GATE> 任何既有测试新失败 → 不得进入提交。先排查是否修复引入了回归。 </HARD-GATE>

---

## Step 6: 提交 + 回填

**原子提交**（硬规则 4）：修复 + 测试同入一个提交：

```
fix(<scope>): <错在哪、现在对了>

Root cause: <一句话>

Fixes: #<issue 编号>（如适用）
```

**立即捕获 commit_hash**：提交后马上 `git rev-parse HEAD`——并发安全锚，晚一步并发提交就取错。随即 `resolveBug`（outcome=fixed，bug_id + commit_hash + **fix_approach**）；worktree/branch、修复者与修复会话由工具以 hash 为锚反查，不要手填。回填不得拖延：提交→hash→resolveBug 一气呵成，零并发窗口。

**fix_approach（fixed 必答）**：一段话写清采用了什么修法、**落点层级（根因级/症状级）**、为何选此法而非替代方案（关键取舍、遗留兜底）——bug 台账的审查面，与 Root cause 注记互补（后者讲为什么发生，前者讲怎么修）。

**生效路径注记（交付必答）**：用户验证 ≠ 提交即生效。摘要必须写明：哪些面需重建（前端 bundle——刷新页面不重建）、哪些需重启宿主进程、哪些只对新产生的数据生效（旧数据走旧路径/兜底）。

**输出摘要**：

```
Bug Fix Summary
───────────────
Bug:     <描述>
Fix:     <改动文件>
Approach:<修复方案总结——同 fix_approach>
Tests:   <N 个单元测试> + <M 个 E2E 测试>
Result:  全部通过 ✓
Commit:  <hash>
生效:    <重建/重启/仅对新数据生效——用户验证前置动作>
```

---

## 边界

- 琐碎修复（错字/配置，无行为面）可裁断跳过 Step 1-3 的完整分析，但台账两阶段与原子提交（硬规则 4）不豁免。
- 全量跑 exit code 非零不径直判失败：先看测试汇总行，环境噪音与结果分离判读。
