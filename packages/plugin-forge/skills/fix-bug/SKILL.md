# 修缺陷（Fix Bug）

系统化缺陷修复流程：**理解 → 复现 → 失败测试 → 修复 → 验证 → 提交**。

核心原则：**失败测试证明 bug 在场之前，不碰任何产品码。**

## 编码纪律

- **先想后写**：动手前用自己的话复述 bug 与疑似根因，用证据检验诊断——不轻信第一个看似合理的解释；根因含糊就继续排查。
- **承重假设源头核销**：修复设计依赖的跨包/跨层事实（他包字段形状、写入口径、上游行为），必须读源头实现或实测核销，不靠推断——单元测试红绿只证明本仓逻辑自洽，不构成对上游行为的验证；核销不了的假设 = 方案未定，不得动手。
- **根因上探**：修复面若在用启发式（扫描、字符串匹配、时间戳择新）逆向重建某个未持久化的事实，病根大概率在数据层——诊断上探至「这个事实在哪诞生、为何不在库侧」，数据级与症状级两案并呈，由用户裁决。
- **易变字段不作锚**：面向人的可变字段（标题、显示名、标签）不作关联/判别键——用持久化标识，或推动该事实持久化。
- **最小修复**：只修坏掉的东西。不做投机改动、不做"顺路"优化、不重构；琐碎修复（错字、配置）自行裁断是否需要完整分析。
- **外科手术式改动**：只改失败路径上的代码。不碰邻近代码、不重排无关行、不顺手整理切向逻辑。范围边界 = 失败代码路径。
- **目标导向**：定义清晰可验证的成功条件——修复前失败的那些测试、修复后必须通过。实现后确认条件达成，未达成就迭代。

## 四条硬规则

<HARD-RULE>
1. **复现失败即停**：bug 无法在当前代码库复现 → 停止流程（见 Step 2 HARD-GATE），并仍须调用 `resolveBug` 将已登记的记录回填为 unresolved（附原因）。
2. **失败测试先行**：产品码改动之前，测试必须**因这个 bug 而失败**。修复前测试就通过= 测试没有捕获 bug，改测试直到它因正确的原因失败。
3. **质量门四门序列**：compile → fmt → lint → unit-test，严格顺序、首败即停。具体命令由你根据本仓库实际工具链自行决策——**禁止机械套用固定配方**；任何门失败都不得进入提交。
4. **原子提交**：修复与测试必须同入一个原子提交；提交信息含一句 Root cause 注记（为什么发生，而不只是改了什么）。
</HARD-RULE>

## 输入语义

用户调用时通常携带两类信息（散文表述，不作机械参数解析）：

- **缺陷描述**：报错信息、issue 编号或一段现象描述——缺席时在 Step 1 排查中交互补齐。
- **范围提示**：受影响的模块/包路径——缺席时自行探测（从症状关键词与栈追踪定位）。

## Step 1: 理解 bug

动任何代码之前收集全部上下文。

**项目规范与惯例搜集（义务，手段不限）**：从 bug 描述、受影响文件与范围推断相关领域，搜集本项目的规范、惯例与既有决策——知识库检索、`AGENTS.md`、`docs/` 等均可，**不强制特定 skill 或工具**。无相关规范时明确说明后跳过。

**收集**：bug 描述 / 报错信息 / 栈追踪；复现步骤（来自 issue 或用户）；期望 vs 实际行为；受影响版本 / 提交（未知时查最近提交历史）。

**定位爆炸半径**：用仓库内检索工具（grep/glob/read 等，按你环境实际具备的为准）找症状相关文件，查可疑文件的变更历史。

**承重假设核销（义务）**：列出修复设计将依赖的全部跨包/跨层假设，逐条以源头证据（上游包源码、宿主实现、实测输出）核销——本包测试全绿不构成对上游行为的验证；核销不了的假设 = 修复方案未定，不得进入修复步。

**产出 Bug Summary**（继续之前必须成文）：

```
Bug:       <哪里出了问题>
Trigger:   <触发该问题的确切步骤或输入>
Expected:  <正确行为>
Actual:    <观察到的行为>
Suspected: <疑似位置 file:line 或模块>
```

**落库（第一阶段）**：Bug Summary 成文后立即调用 `recordBug` 登记——提交 summary（一句话 ≤50 字）+ 五字段 + 可选错误类型标注；记录返回的 bug_id，Step 6 回填时引用。身份、会话与仓库态由工具自行解析，**不要手填**。

---

## Step 2: 复现

在当前代码库确认 bug 可复现，然后才写任何测试。

- 先跑基线测试套件，确认全绿（无既有失败掩盖 bug）。
- 在基线之上重现 bug，把确切复现步骤记录下来。

<HARD-GATE>
无法复现 → **STOP**。不得为未确认的 bug 写测试或改代码。向用户报告排查发现，并调用 `resolveBug`（outcome=unresolved，附 unresolved_reason——写明停机原因，通常即 Step 1 排查结论）。流程到此为止。
</HARD-GATE>

---

## Step 3: 写失败测试

写出**因 bug 而失败、修复后通过**的测试——这是修复有效的证明。

**单元测试**：找到离缺陷代码最近的测试文件（沿本仓库既有测试布局惯例），加一个聚焦用例。命名描述错误行为，如 `bug: 输入为空字符串时返回 null`。

运行单元测试——**修复前必须失败**：

<HARD-RULE>
修复前新测试就通过 = 测试没有捕获 bug。修改测试直到它因正确的原因失败。
</HARD-RULE>

**表面级测试**：仅当 bug 在 API / CLI / UI / mobile / TUI 表面可观察时补加——放入对应 surface 的旅程测试目录，同样修复前必须失败。纯内部缺陷不需要。

---

## Step 4: 修复

失败测试就位后，实现最小修复。

- 恪守编码纪律——最小修复与外科手术式改动定义范围边界。
- 根因在依赖里时，记录之并施加最小 workaround。
- **方案分级呈报**：「能过测试的最小修复」若属脆弱面（启发式重建未落库事实、易变字段作锚、对上游行为打补丁），不径直提交——向用户并案呈报「症状级补丁 vs 根治级方案」由用户裁决；根治级常涉契约面/持久化变更，本就该用户拍板。
- 同一 bug 修复后再次被报 → 先复核已交付修复的承重假设（多半是某假设在真实环境失配），再考虑新排查。

**Root cause 注记**：写一句到代码注释或提交正文：

```
// Root cause: <为什么会发生，而不只是改了什么>
```

---

## Step 5: 验证（质量门）

执行四门序列（硬规则 3）——**compile → fmt → lint → unit-test**，严格顺序、首败即停：

| 门 | 失败处置 |
|---|---|
| compile | 修复后重跑 |
| fmt | 非阻断警告，按提示格式化 |
| lint | 自修（至多 1 次重试），仍败 → blocked |
| unit-test | 修复后重跑 |

Step 3 写了表面级测试的，一并运行。验证清单：新测试全过；既有测试零回归；构建成功（如适用）。

<HARD-GATE>
任何既有测试新失败 → 不得进入提交。先排查是否修复引入了回归。
</HARD-GATE>

---

## Step 6: 提交 + 回填

**原子提交**：修复 + 测试同入一个提交。提交信息格式：

```
fix(<scope>): <错在哪、现在对了>

Root cause: <一句话>

Fixes: #<issue 编号>（如适用）
```

**立即捕获 commit_hash**：提交完成后马上 `git rev-parse HEAD`（或等价命令）记下提交哈希——这是并发安全锚，晚一步并发提交就取错。**落库（第二阶段）**：随即调用 `resolveBug`（outcome=fixed，提交 bug_id + commit_hash + **fix_approach**）；worktree/branch、修复者与修复会话由工具以 hash 为锚反查，不要手填。

**fix_approach（修复方案总结，fixed 必答）**：一段话写清**采用了什么修法、为何选此修法而非替代方案**（落点层级、关键取舍、遗留的兜底径）——bug 台账的审查面，供不进 git 的人审阅；与 commit message 的 Root cause 注记互补（后者讲为什么发生，前者讲怎么修的）。

**生效路径注记（交付必答）**：用户验证 ≠ 提交即生效。摘要必须写明：哪些面需要重建（前端 bundle——刷新页面不重建）、哪些需要重启宿主进程、哪些只对**新产生的数据**生效（旧数据仍走旧路径/兜底）。缺此注记，用户按旧方式验证必然误报「没修好」。

**输出摘要**（完成后报告）：

```
Bug Fix Summary
───────────────
Bug:     <描述>
Fix:     <改动文件>
Approach:<修复方案总结——同 fix_approach>
Tests:   <N 个单元测试> + <M 个表面级测试>
Result:  全部通过 ✓
Commit:  <hash>
生效:    <重建/重启/仅对新数据生效——用户验证前置动作>
```

## 常见陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 写失败测试之前就修 | 永远测试先行 |
| 修复前测试就通过 | 测试没捕获 bug——改测试 |
| 修的比 bug 多 | 只做最小修复；清理另开任务 |
| 用户可感知的 bug 不加表面测试 | 至少补一个表面级冒烟测试 |
| 修复与测试分开提交 | 一个原子提交：fix + tests 在一起 |
| 提交后拖延回填 | 提交→捕获 hash→resolveBug 一气呵成，零并发窗口 |
| 测试全绿 = 假设为真 | 失败测试只证本仓逻辑——跨包假设读源头核销 |
| 展示字段（标题/label）当判别键 | 会被自动生成/重命名遮蔽——用落库事实或让事实落库 |
| UI 启发式重建未落库事实当"修好" | 病根在数据层——症状级/根治级并案呈报用户裁决 |
| fixed 回填只交 commit_hash | fix_approach 必答——台账审查面不进 git |
| 提交即让用户验证 | 前端要重建、宿主要重启、旧数据走旧路径——生效路径写入摘要 |
| 全量跑 exit code 非零就判失败 | 先看测试汇总行——环境噪音与结果分离判读 |
