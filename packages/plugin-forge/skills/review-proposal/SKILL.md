# 提案评审（review-proposal）

proposal.md 成稿后、用户裁决前——报告是 accept/reject 裁决的输入。核心一问：**能否以周密的方案、清晰地满足需求？**四问展开见下。提案层不做技术选型；只出报告不改提案，返工权归 brainstorm。

## 执行机制：独立 subagent

- 主会话只做两件事：**组装简报**（proposal 路径、仓库根；不含讨论过程与预期结论）与**转呈结果**。
- subagent 不继承主会话上下文，结论以自己读到的提案与代码为据；报告落盘 `proposals/<slug>/review/report.md`，主会话不改报告，只做后续处置。

## 评审四问

### 突击同步核对项（条件化，与远征链口径一致）

仅当提案交付物触及 **UI/交互面或运行期装配面**时逐项核对（短平快、纯逻辑/纯文档提案不启用；不触发不判缺陷）：

- **真机取证 AC**——涉运行期装配面（进程、网络端点、真实调度/时钟、对外部系统的真实副作用）的交付面，对应任务/验收是否写明真机取证方式与取证环境；缺失 = Blocker。
- **待裁决清单/裁决台账**——涉 UI/交互面时，「待用户裁决清单」段是否在场（微文案、布局终态、交互词汇等只有用户能判的决策点，无则写「无」）；飞轮派生提案（`parent_proposal_id` 在场）是否带指标对比附录段；缺失 = Blocker。
- **官方核销结论**——官方/外部机械装配面的 API 引用是否有源码出处的核销结论；无出处 = Blocker。
- **wakeup 信息集五要素**——凡提案含**新增 wakeup 径**（异常唤醒、guard 粘住、suspendWithWakeup、终局结算等），验收标准（AC）是否对唤醒消息**逐要素断言**五要素：任务标识（slug/local-id）、错误原文（长文附全文引用）、发生阶段、重试计数、处置入口（信息集正本见 `docs/conventions/wakeup-notification-minimal-info-set.md`）；任一要素缺失 = Blocker。

1. **需求满足吗**——In Scope 每条需求都有对应方案（漏了 = 覆盖不全）；方案解的是真需求，不是把手段当成了目的；交付物边界与需求对等（不多不少）；假设的既有能力/官方机制真实存在（读源码验证，优先复用官方既有机制）。
2. **方案周密吗**——直击根因还是在症状上修修补补（逐条追问为什么需要，答不到需求层 = 贴补丁）；边界情况、失败路径、迁移/兼容后果被考虑（漏了哪类 = 问题）；有没有更简单的整体方案被跳过。
3. **改动收敛吗**——改动面最小吗？新增的机制、文件、依赖各有不可替代的理由吗；抽象层是为当下需求还是想象的未来；对宿主与上游官方包的改动是否只落在官方扩展点与最小装配处。
4. **表述清晰吗**——方案可被唯一理解（无歧义词、关键术语有定义）；验收标准明确可测（现有测试设施可执行）；改动面与影响范围陈述与代码库实际相符。

## 输出与处置

报告问题三级：

| 级别 | 判据 | 处置 |
|---|---|---|
| **Blocker** | 需求覆盖有洞 / 假设不成立 / 修修补补错位根因 / 改动面不收敛 / 表述歧义致验收不可测 | 返工提案（brainstorm 修订），重评清零才提请用户裁决 |
| **Question** | 权衡可辩，agent 无法单方裁定 | 并入报告呈用户（裁决时一并定）；派发语境呈报于任务输出 |
| **Note** | 不阻塞的改进建议 | 留档 |

- 每个问题附**证据**（文件:行 / 提案段落）；「更周到/更简单」的断言必须给出具体替代方案，不接受空评。
- 放行判据 = Blocker 清零；报告 + 未决 Question 一并呈用户裁决，报告尾记录放行结论。
- 交互语境：Blocker 清零后报告随裁决请求呈用户。派发语境（doc-review 任务）：worker 即独立上下文直接执行，无 Blocker 按简报结算。
