# 运行测试（Run Tests）

**核心原则**：这是一个编排器——发现旅程、按序执行测试、如实上报实测结果。旅程发现、服务生命周期、结果解析与上报都在这里完成——仅此而已。修复、重写测试、下判定属于别处（发起任务与 fix 链）。

**按需加载**：这份文档只在执行 `test-run` 任务时适用——手上没有 test-run 任务却在读它，就把它放回去。

<HARD-GATE>

- 不修改测试脚本内容。
- 不跳过失败的测试，也不把失败报成通过——跑了什么就报什么。
- 不在执行过程中"修好"测试让它通过。测试脚本的 bug 可以上报；为了强行通过而改动断言或逻辑即属伪造。
- 同一编排周期内，probe 失败后不重试 probe、不重启 dev（任务层做出修复决定后的新一次调用属于新周期）。
- 以任务身份运行时（`type: test-run`）：任何失败都以 `submitTask result=blocked` 结算，并在 reason 中写明失败的旅程与用例——绝不带着已知失败提交 `success`。失败不在此处内联修复；修复决定属于发起任务。

</HARD-GATE>

## 何时使用

- 认领了一个 `test-run` 任务（为某个容器做测试执行），或
- 用户要求运行测试。

当没有可运行的旅程测试时，明确声明后跳过——不要改跑别的。

## 判断点（按顺序）

1. **装载测试策略**——探测工作区 `docs/conventions/testing/`（应用向测试链声明的策略与约束正本）：在场即装载遵循——dev/probe/test/teardown 命令、旅程发现口径、执行约束（run-once、环境前提）优先取自该处；缺席则按仓库事实推导并在报告中记录判据。探测零结果不是错误。
2. **发现旅程**——**模块归属**（monorepo，全链统一判据：每条 Journey 唯一目标模块 = workspace 包/应用目录，权威载体 = journey frontmatter `module` 字段；单仓省略）。按工作区实际测试树探测：单仓 `tests/<journey>/`；monorepo 逐模块 `<module>/tests/<journey>/`（模块测试根以其框架配置 testDir 为准；无 journey 文档可引时以测试树为准并在报告中记录判据）。未发现任何旅程 → **阻断性**错误，不可重试：连同探测证据一并上报并停止。以任务身份被调用且未限定旅程范围 → 运行全部已发现的旅程。
3. **检查环境**——测试命令及其依赖存在且可运行。不就绪 → 以**可重试**中止（环境可被修复后重新调用本技能）；只上报诊断信息与修复建议——不自动修。
4. **执行序列**——工作区具备服务生命周期（可运行的 dev 启动与 probe 探活）：dev 一次 → probe（有界重试，约 3 次）→ 逐旅程以 **run-once** 测试命令执行（命令按工作区实际工具链取用，如 `npx playwright test <journey>` / `npx vitest run <journey>`；一律 run-once，禁 `--watch` 形态）→ teardown 一次。无服务生命周期：逐旅程循环 → teardown。每个旅程完成即记录其结果。teardown 是**强制的——即使前面步骤失败也必须执行**。
5. **上报**——每个旅程的合计（passed/failed/skipped）、每条失败附错误摘录作为证据、以及实际执行的序列。结果输出缺失或为空 → 如实说明并附运行器控制台输出；不得编造报告。

## 结算（以任务身份运行时）

按 submit-task 纪律结算：

- 全绿 → `submitTask result=success`，报告作为 summary。
- 任何失败 → `submitTask result=blocked`，reason 写明失败的旅程与用例；修复承接走 fix 链——由主会话/循环处置层派生修复任务，本技能不做任何修复决定。

这里绝不允许为强行通过而编辑测试脚本——因此此处没有任何可供提交的改动。
