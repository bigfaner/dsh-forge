# Brainstorm（头脑风暴）

从模糊想法到结构化提案，经由不留情面的协作对话。目标是达成真正的共识——不是过滤想法，而是把隐含假设显式化，让正确的路径自然浮现。伪需求在思考清晰后自然消亡。

<HARD-GATE> 禁止写代码或执行任何实现动作——本技能只产出 proposal 文档及其 proposal 域记录行。 </HARD-GATE>

<HARD-RULE> **不做技术选型；只谈约束。** 描述"要达成什么效果"（性能、平台、安全）——而非"用什么工具实现"（框架、语言、数据库、模式）。技术选型属于 tech-design。 </HARD-RULE>

## 流程总览

```
分析上下文 → 走设计树 → 提出方案 → 圈定范围 → 推断意图 → 撰写提案 → 一致性检查 → 用户批准 → 注册
```

### Step 1：分析上下文

提问之前，先检索代码库中的相关特性、文档、提案与近期历史。综合结论内部消化——不要把分析过程抛给用户；它驱动有依据的提问。

### Step 2：走设计树

持续访谈直到达成真正的共识——而非表面同意。

#### 时序主线

树的第一问是根本需求本身：把 Step 1 消化出的需求界定提请用户批准——「我理解的需求是 X；备选需求 Y、Z」——根本需求经批准，树才往下生长；未经批准即沉默假设。

提问一律经 `ask_user_question` 工具发出（推荐答案 = 首选项）。缺省一次只问一个问题；当多个问题互不依赖且各自前置已裁决时，可一轮打包——一次调用携带多题，每题编号、推荐项置首，收齐答复再进下一轮。**先给出你的推荐答案**；若问题可以通过探索代码库回答，就去探索而不是提问。

父决策（有子分支者）在给出推荐前先呈备选空间——至少两个真备选供比对，不得以单选假象收敛。先解决父决策再进入子分支（若 B 依赖 A，先定 A）；当某分支推翻更早的假设时回溯。

访谈终止 = 设计树全分支裁决：凡前置已决、现在就能问的问题都已问出口并得到裁决，问题级与选项级皆无沉默假设——未问出口的问题不得默认成立，未呈出的备选不得默认排除。

终止后复述审核：全部问题裁决完毕、进入 Step 3 之前，逐条复述所有问答与答案（每问 + 用户的最终裁决），供用户整体审核确认；复述末尾必附一问——「以上是全部裁决，有没有我该问而没问的？」——以此补出未问之问。用户更正任何一条即回溯该分支重决，复述以更正后的裁决为准。

#### 横切纪律

发散先于收敛，探索免举证：树形落定前允许无证据前提的探索性提问——如果……会怎样？反过来呢？相邻需求是否才是真需求？证据门只治理挑战（质疑既有主张），不治理探索（扩展可能性空间）——但探索须有落点：每个探索性提问归档于其服务的决策点或对根本需求的疑问（内部归档，问句不必自报家门）。多分支或非平凡的探索至少取用一次「方法论速查」中的手法（双钻、SCAMPER、机会解决方案树……）对当前需求界定做一轮重构检验——单分支小想法可豁免该检验，但对根本需求的批准与复述审核永不豁免；不得只靠临场直觉单源发散。根本需求亦可推翻：一旦探索表明找错了根本需求，回退重新界定（Need Gate 第 2 问常是入口），不止在树内回溯。

挑战内嵌于每个决策点，不是独立阶段：每次挑战必须引用代码库事实、逻辑一致性或领域常识——先陈述观察 → 出示证据 → 抛出问题。理性审慎，绝不敌对。

**需求闸门（Need Gate）**——深入每个具体特性的*怎么做*之前，按序检查：
(1) _有更简单的替代？_ 现有工具/组合已能解决 → 提议那条路；
(2) _真实需求是什么？_ 假设底层目标并在评估此路是否最优前先确认它；
(3) _为什么是现在？_ 延后成本低 → 建议延后。
若用户否决闸门，接受并在提案中记录 `Challenge Override: user chose to proceed. Reason: <原因或"未说明">`——否决之后不再继续纠缠。

### Step 3：提出方案

提出 2–3 个**业务方案**（不是技术实现）。推荐项放最前，附诚实的权衡取舍，并始终把"什么都不做"作为备选之一。对比时**必须识别跨模块/服务交互面**：谁与谁交互、涉及哪些流程、边界在哪里——这些是 tech-design 精确设计契约的输入。由用户决策。

### Step 4：圈定范围

在交付物层面提出纳入/排除边界。取得明确同意；若过大，建议拆分。

### Step 5：推断意图

从方案与范围（不是标题）推断 frontmatter `intent`：任何新的外部可观察行为 → `new-feature`；纯内部重组 → `refactor`；其余按最接近者取 `enhancement` / `cleanup` / `fix` / `doc`。给出推理过程呈现给用户——用户可否决。

### Step 6：撰写提案

通过文件工具写提案文档（`<slug>` proposal 目录相对约定——存储布局见 forge-pipeline 系统提示段「文档位置/目录树」），含 frontmatter（`created`、`author` 取自 git config 或用户、`status: Draft`、`intent`）。质量标准——每条都是硬杠：

| 段落         | 标准                                                                                                          | 红旗             |
| ------------ | ------------------------------------------------------------------------------------------------------------- | ---------------- |
| 需求         | 具体陈述 + 证据 + 紧迫性                                                                                      | "我们需要改进 X" |
| 方案         | 具体的用户可感知行为，**优先用 mermaid 图表**呈现方案结构/流程；含跨模块/服务交互面识别                       | "建一个系统……"   |
| 改动影响范围 | 交付物级条目，有边界；受影响的模块/包/交互面点列清楚                                                          | 模糊区域、无边界 |
| 风险         | 3+ 条具体风险及可执行缓解——**仅远征六段含此段**；突击成文五段不含风险（见 forge:pipeline 系统提示段突击语义） | "我们会处理好的" |
| 验收         | 可度量、可测试、覆盖全部范围                                                                                  | "运行良好"       |

方案段不留调整修复类叙事——只写目标形态；过程性讨论留在对话记录，不进提案正文。关键术语随首次出现即以定义句固化（X = ……）；对话中的临时说法不进正文——术语没有定义句，就是没有裁决。

**一致性检查（批准前强制）**：写完验收与纳入范围后做双向核对——每条验收都有某个纳入项满足，每个纳入项都服务于某条验收；任何两条验收不得互相矛盾。发现冲突即呈现给用户并在继续前解决；核对结果记录进提案。

不要自动提交；呈现提案，等待用户明确批准。

### Step 7：注册提案

把已批准的提案注册进状态层——记录行（而非文件树）才是流水线的真相：

```
createProposal { slug: "<slug>", title: "<title>",
                 rel_path: "proposals/<slug>/proposal.md" }
```

## 方法论速查

按需取用（多分支/非平凡探索至少取用其一——见 Step 2 横切纪律），名称 + 一句话 + 适用场景：

- **双钻模型**：先发散再收敛、两轮循环——问题空间含糊、需先定义问题再求解时。
- **影响地图**：目标 → 角色 → 影响 → 交付物——需要把"为什么做"追溯到"做什么"时。
- **机会解决方案树**：机会优先、方案后挂——多机会并列、择优切入时。
- **用户故事地图**：横轴流程、纵轴优先级——范围切分与里程碑排序时。
- **六顶思考帽**：事实/情感/风险/益处/创意/流程分角色审视——方案评审防止单视角时。
- **SCAMPER**：替换/组合/调整/修改/另作他用/消除/重排——改进既有事物找突破口时。
