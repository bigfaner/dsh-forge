# ADR：forge 边界修订（声明 + 工作台 UI + 专家池）

日期：2026-11-23
状态：已采纳

## 背景

主提案裁决 12 曾将 forge 组合器的边界定为「纯声明物化器」：forge 只负责把声明（预设组合、配置清单）物化为实际装载的组合，不承担运行期交互界面与资源池管理。随着专家池场景（experts 服务的注册、编队与消费）进入实际使用，该边界在两点上暴露不足：

1. 组合声明之外缺少一个可操作的工作台面（workbench UI），用户查看与调整组合只能回到纯文本声明，编辑回路长。
2. 专家池作为共享资源池（专家注册、编队、按需挂载）无法用「一次性声明物化」表达——池的生命周期长于单次组合，且需被多个组合点消费。

## 决策

- 推翻主提案裁决 12 的「纯声明物化器」口径，将 forge 边界修订为三段：**声明物化 + 工作台 UI + 专家池**。
- 三段中按增量分批落地：**工作台 UI 为未来增量，本次不实现**；本次只落专家池。
- 本 ADR 即裁决翻案的留痕：边界变更以 ADR 记录，主提案原文不再单独修订。

## 理由

- 纯声明口径对「一次性组合」成立，但对跨组合共享、长生命周期的资源（专家）表达力不足——池需要独立于单次物化的存在面，强行塞进声明物化会造成声明模型扭曲。
- 工作台 UI 是对声明编辑回路的自然补全，但其形态与官方组件复用面（§3.1 对齐纪律）尚需设计，先划入边界、后做增量，避免边界外能力事后翻案第二次。
- 专家池已有明确消费方（expert-squad 对 experts 服务的在场性消费），需求真实且收敛，优先落地。

## 影响

- forge 组合器的职责面从单一物化器扩展为三项能力域；后续提案与设计须按新边界评估归属。
- 专家池在本 ADR 之后落地为首个增量；工作台 UI 保持「已入边界、未排期」状态，待设计与官方组件对齐走查后再启动。
- 主提案裁决 12 自本 ADR 起失效，引用处以本 ADR 为准。
